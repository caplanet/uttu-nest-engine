## 1. 이 작업이 무엇인가

`AdaptiveAlgorithm` 은 2D 불규칙 strip packing(의류 마커 네스팅) 솔버다.
Rust 워크스페이스 + C ABI(cdylib `capswarmcore_100`) + WPF 샘플.

```
swarm-core   알고리즘 본체 (초기 배치 / 탐색 / 압축 / 후처리)
swarm-nfp    NFP 커널 (Clipper2 i64 정수 격자)
src/           C ABI (ffi.rs, ffi_step.rs) — **WPF 는 ffi_step 의 step API 를 쓴다**
csharp/        C# 바인딩 + WPF 샘플
```

파이프라인:

```
초기 배치 → 탐색(exploration) → 압축(compression) → 후처리(polish)
```

기준 데이터: `data/input/wsjk156.json` (156조각 의류 마커).
사용자가 지정한 `여성WSjk_비교용-G_New_Swarm_신규2.json` 과 **sha256 이 같다.**

## 5. 되돌리기 전에 읽을 설계 결정

### 5-1. Clp / Xpress 를 빌드에 링크하지 않는다

둘 다 빌드 시점에 벤더 SDK 를 요구하고 Xpress 는 라이선스도 필요하다.
`Cargo.toml` 에 박으면 **SDK 없는 모든 환경에서 빌드가 깨진다.**
그래서 C ABI 를 `libloading` 으로 **런타임 동적 로딩**한다.

```
Clp     clp.dll / libClp.so       환경변수 SWARM_CLP_LIB
Xpress  xprs.dll / libxprs.so     환경변수 SWARM_XPRESS_LIB
```

없으면 `fallback` 설정에 따라 microlp 로 물러나거나 압축을 건너뛴다.
**QP 는 라이선스 없이도 풀린다** — `clarabel`(순수 Rust 내점법)이 있다.

### 5-2. LP 압축은 이제 한 경로다 (통합 완료)

예전에는 기본 경로(인라인 microlp)와 일반화 경로가 갈려 있었다. 등가성을 **합치기 전에**
테스트로 증명하고(제약 개수·계수·우변, 목적값·해 전부 대조) 합쳤다. 실 인스턴스에서
제한을 풀면 폭이 **비트 단위로 재현**된다.

그 과정에서 `microlp_backend` 의 사후 예산 판정이 **증명된 최적해를 버리고 있었다**.
microlp 0.6 순수 LP 에서 `Solution` 은 언제나 증명된 최적해이고(데드라인은 값 없이
`Interrupted` 로 온다), 압축은 어차피 CDE 로 사후 검증한다. 지금은 버리지 않는다.

### 5-3. `adaptive_probe_budget` 은 기본 **꺼짐**이다

내가 넣었다가 되돌린 기능이다. 두 가지 문제가 있었다.

1. **결과가 벽시계에 의존한다.** 조절 판정이 `Instant::now()` 실측을 쓰므로 같은 입력이
   머신·부하에 따라 다른 배치를 낸다.
2. **문서와 다르게 동작한다.** 호출부가 placer 를 `max_candidate_probes` 로 시작시키고
   같은 값을 상한으로 넘기므로 "2배로 올린다" 분기는 **처음부터 도달할 수 없다.**
   실제 동작은 시간이 모자랄 때 정밀도를 깎는 안전밸브 하나뿐이고, **그게 이득인지는
   재지 않았다.**

두 사실을 테스트로 못 박아 뒀다(`adaptive_probe_budget_is_off_by_default...`,
`in_the_real_call_shape_the_budget_can_only_go_down`).

### 5-4. 병렬화는 **결정론이 통과 조건**이다

사용자 지시: *"병렬로 돌려도 문제가 없어야 하는 조건이야."*

이 코드베이스는 회귀를 비트 단위 비교로 잡는다. 병렬 축약이 순서에 의존하면 모든
실측치가 무의미해진다. 그래서 `accrete.rs` 에서 이렇게 했다.

* **epsilon 비교를 버리고 양자화한 정수 키**를 쓴다. `|a-b| <= eps` 는 **추이성이
  깨져서**(`a~b`, `b~c` 인데 `a<c`) 훑는 순서에 따라 최댓값이 달라진다. 양자화는 값
  하나만 보고 정수로 떨어뜨리므로 정의상 추이적이다.
* 마지막 타이브레이크가 **전역 유일한 인덱스**라 최댓값이 하나로 정해진다.
* **청크 크기를 스레드 수에서 뗐다**(`CHUNK = 1`). `tier.len()/스레드수` 로 나누면
  같은 입력이 머신마다 다르게 분할된다.

검증: `tests/nfp_parallel_determinism.rs` 4종 — 반복 8회 / 스레드 1·2·3·5·8·16 /
156조각 × 스레드 1·3·16 / 조각 보존. 전부 **비트 단위** 비교다.

**새로 병렬화하는 코드는 이 4종을 통과해야 한다.**

## 6. 남은 작업 — 우선순위

### 6-1. 【높음】 슬라이딩 압축 병렬화

현재 5초 예산 분해:

```
prewarm     782ms  (이미 병렬)
누적 배치  1,800ms  (병렬, 16코어)
슬라이딩   2,493ms  (**단일 스레드**)  <- 지배항
합계       5,075ms
```

슬라이딩이 절반을 먹으면서 코어 15개가 논다. 이걸 풀면 5초 예산에 **2초가 남고**,
그 시간으로 라운드를 늘리거나 누적 배치를 다중 시작으로 돌릴 수 있다.

난점: 조각 i 를 옮기면 i+1 이 보는 장애물이 달라진다 — **진짜 루프 반송 의존**이다.
재구조화 후보: "한 라운드 안에서는 원래 배치를 기준으로 전부 평가하고, 채택만 순차로".
그러면 결과가 달라지므로 **품질을 재서** 판단해야 한다.

### 6-2. 【높음】 5초 예산 안으로 되돌리기

지금 5,075ms 로 목표를 75ms 넘는다. 6-1 이 해결하면 자동으로 들어온다.
그 전에도 prewarm(782ms)을 배치와 겹치게 하면 여유가 생긴다.

### 6-3. 【높음】 접촉 지표를 전략 계층까지 정확하게

`feasible_touch_count` 가 **정확한 접촉 조각 수**를 이미 돌려준다(feasible 판정이
obstacle 마다 계산하던 `Location::Boundary` 를 센 값이라 공짜다).

`accrete.rs` 는 오라클에서 직접 받아 쓰지만, `nfp_strategy::AnchorMetrics` 에는
아직 없다. 넣으면 ③ 접촉 최대화와 ⑤ 빔이 정확한 신호를 쓴다.

**패치는 준비돼 있다**: `scratchpad/exact_contact3.py` 에 `AnchorOption.touches` +
`AnchorMetrics.touches` + `select::cmp_by_rule` 배선이 들어 있다. 워크플로가 같은
파일을 편집 중이라 미뤘다. 워크플로가 끝나면 적용하고 재측정할 것.

> 주의: `AnchorOption` 에 필드를 더하면 `beam.rs`/`pipeline.rs` 의 구조체 리터럴이
> 깨진다. 함께 고쳐야 한다.

### 6-4. 【중간】 누적 배치를 설정으로 노출

`accrete.rs` 는 아직 `NfpStrategyConfig` 에 스위치가 없다. 벤치에서 직접 호출만 한다.
전략 ⑧로 추가하고 ABI v11 tail block + C#/WPF 컨트롤을 붙여야 실제로 쓸 수 있다.

### 6-8. 【최우선】 누적 배치 + 꼬리 회수를 합쳐 재 볼 것

## 8. 이 코드베이스에서 반복해서 밟은 함정

새로 들어오는 사람이 같은 걸 밟지 않도록 남긴다.

1. **설정을 만들고 배선을 잊는다.** 이 세션에서 **두 번** 겪었다. 모듈·ABI·UI 를 다
   만들어 놓고 호출하는 줄이 없어 기능이 통째로 죽어 있었다. 빌드도 테스트도 통과했다.
   → `to_config` 가 전략을 **인자로 받게** 바꿔 컴파일러가 막게 했고,
     소스에 진입점이 등장하는지 단정하는 **회귀 테스트**를 `search.rs` 와
     `ffi_step.rs` 에 넣었다. 새 기능을 배선할 때 같은 테스트를 추가할 것.

2. **정규화한 값에 mm 단위 허용오차를 쓴다.** 축마다 나누는 기준이 다르면 같은 1mm
   차이가 축에 따라 동률이 되기도 하고 아니기도 한다. 우선순위 비교는 **실제 mm 값**으로.

3. **bbox 근사를 실제 기하로 착각한다.** 접촉 지표가 bbox 겹침을 접촉 0 으로 쳤고,
   포켓 경계가 조각 폭 대신 IFP 폭을 뺐다. 둘 다 "같은 함수 안에 있던 비슷한 이름의
   값" 을 잘못 쓴 것이다.

4. **낡은 실측치를 근거로 상수를 고른다.** 탐침 예산 1024 는 `NfpMask`/`locate_prepared`
   도입 **이전** 측정("4096 = 19.90초")을 근거로 골랐다. 지금은 12초다.
   → 주석에 수치를 남길 때 **측정 조건을 함께** 적을 것.

5. **A/B 에 예산 정책을 섞는다.** `scale_orderings` 가 전략 비용만큼 ordering 을
   줄이는데, 그대로 A/B 하면 "전략이 나쁜 것" 과 "덜 돈 것" 이 섞인다.
   실제로 첫 측정에서 팔마다 12/8/6/3/1 개로 갈려 있었다.

6. **epsilon 비교로 병렬 축약을 한다.** §5-3.

## 9-B. LBF 방향성 오목도 정렬 (`LBF수정사항.md` 구현, 2026-08-31)

`LbfOrderMode` 에 두 모드를 더했다. 정렬 **키** 자체를 바꾸는 첫 모드다
(기존 넷은 크기 점수의 순회 방향만 바꿨다).

| raw | 모드 | 정렬 키 |
|---|---|---|
| 4 | `ConcavityFirst` (오목도부터) | `10·S_L + S_B + 2·S_C + 0.5·S_D` 내림차순, 동점은 크기 |
| 5 | `SizeTimesConcavity` (크기×오목도) | `크기 × (1 + 점수)` 내림차순 |

`S_L`/`S_B` = 왼쪽/아래로 열린 오목부의 정규화 면적 합, `S_C` = `(hull − poly)/hull`,
`S_D` = 깊이 가중 합. 모듈은 `swarm-core/src/optimizer/concavity.rs` 이고 설계와
다르게 한 곳(불리언 차집합 대신 **볼록껍질 간선 기준 포켓 분해** — 정확하고 외부 크레이트
없음)과 그 근거를 모듈 문서에 적었다. 원본 도형(`shape_orig`)으로 계산한다 —
충돌용 도형은 `narrow_concavity_cutoff` 가 좁은 오목부를 메워 버린다.

배선: `LbfOrderMode::from_raw` 4/5 · `CLbfOrderConfig.mode` 문서 · C# `LbfOrderMode`
enum · WPF 콤보박스 항목 2개 · `lbf_order_feasibility.rs` 여섯 모드.
**ABI 구조체는 안 바뀌었다**(`mode` 는 이미 i32).

### ⚠ 판정은 시드가 아니라 최종 밀도로

`scale-collapse` 브랜치의 실측(`DENSITY_GAP_ANALYSIS.md` §2-4)은 **초기 배치 개선이
최종 밀도로 전달되지 않는다**는 것을 보였다 — 시드 +3.5%p 가 60초 예산에서 전부

이전에 쓰였다. 그래서 오목도 정렬은 **기본 꺼짐**이고, 판정 하네스는 시드와
탐색·압축 뒤 밀도를 **둘 다** 찍는다.

## 9-C. 겹침 허용의 원단 경계 결함 — `scale-collapse` 에서 이식 (2026-08-31)

`piece_overlap_mm = X` 는 jagua importer 오프셋 `-X/2` 가 **아이템과 컨테이너 양쪽**에

양수 이격은 한 비트도 안 바뀐다. 원단 짧은 변의 45% 를 넘는 축소는 상한을 걸어

배선: `ffi_step.rs`(WPF step API) · `grouped_engine.rs`(전체 인스턴스 **와 레인** —

## 9-D. 정지(`StopWait`) 지연 점검 (2026-08-31)

`swarm_request_stop_and_wait` 는 플래그(`Arc<AtomicBool>`)를 세우고 **현재 단계 함수가
반환할 때까지** 기다린다. 지연 = 플래그 이후 그 함수가 빠져나오기까지의 시간이다.
단계별로 플래그를 어디서 보는지 훑었다.

| 구간 | 정지 확인 | 최악 지연 | 판정 |
|---|---|---:|---|
| 탐색 (`separate` 안쪽 루프) | iteration 마다 `term.kill()` | ms 단위 | 양호 — `stop_latency` 하네스가 1.5s 로 못 박음 |
| 압축 (`compression_phase`) | 시도마다 + 안쪽 `separate` | ms 단위 | 양호 |
| 폴리시 라운드 (`polish_phase_*`) | 라운드·패스 경계 + slide/holes 안쪽 | 아래 LP 만큼 | 양호 |
| 폴리시 LP 풀이 | **솔버 안에서는 못 본다.** 시간 제한 `min(마감, time_limit_ms=5s)` 만 | **≤ 5s** | 허용 (문서화) |
| **폴리시 잔여 회수 (`reclaim_leftover`, 기본 켜짐)** | **사이클 시작 시점에만** `outer.stop_requested()` | **남은 폴리시 예산 전부** | **결함 — 고쳤다** |
| 초기 배치 (NFP 시드 `build_best_initial_nest`) | 없음 — 자체 예산 `total_budget_ms`(기본 10s)만 | ≤ 10s | 기본 꺼짐. 켜면 이만큼 |
| 초기 배치 (LBF `construct`) | 없음 | ~1s (wsjk156) | 허용 |
| 단계 반환 뒤 인증 (`solution_validation_error`) | 없음 | 조각쌍 전수 검사, 1s 미만 | 허용 |

### 결함 — 회수 사이클의 터미네이터가 정지 플래그를 몰랐다

`reclaim_leftover` 는 조각마다 `BasicTerminator::new()` 에 시간만 걸어 안쪽
압축·폴리시·R&R·탐색에 넘겼다. 그 터미네이터는 바깥 플래그를 모르고, 바깥 플래그는
사이클 **시작** 시점에만 확인됐다. 그래서 폴리시 도중 정지를 누르면 현재 사이클의
조각 시간 — 남은 폴리시 예산의 75%(압축) + 25%(폴리시) — 이 다할 때까지 멈추지
않았다. 폴리시가 고정점에서 일찍 끝날수록(실측 60s 중 2.4~7.4s) 남는 예산이 크고,
그만큼 정지가 늦었다. "Compress 나 Polish 단계에서 굉장히 오래" 가 정확히 이것이다.

`SliceTerminator` 로 바꿨다 — `kill() = outer.stop_requested() || 조각 마감`.
`outer.kill()` 이 아니라 `stop_requested()` 를 보는 이유는 바깥 폴리시 터미네이터의
시계가 회수 시작 시점에 이미 만료돼 있기 때문이다(원래 주석의 근거 그대로).
전반부(압축/R&R/탐색)가 정지로 잘리면 후반부 폴리시에 들어가지 않고 최선을 유지한다.

회귀 테스트: `tests/stop_latency.rs::reclaim_stops_promptly` — 회수 사이클 한가운데서
정지를 넣고 1.5s 안에 돌아오는지. 고치기 전에는 조각 시간(수십 초)만큼 걸렸다.

### 남은 상한 — LP 풀이 5s

`FractionalTerminator` 가 부모 정지를 물려받지만 **솔버 호출 자체는 폴링하지 못한다.**
한 번의 풀이는 `min(남은 마감, LpSolverConfig::time_limit_ms=5s)` 로 잘린다. 정지가
LP 풀이 도중 들어오면 최대 5s 뒤에 반환한다. 더 줄이려면 `time_limit_ms` 를 내리면
되는데(풀이 품질과 맞바꾼다), 5s 는 허용 범위로 두고 문서화만 한다.

## 9-E. 탐색 궤적 실험 — "목표 폭으로 점프해 놓고 충돌을 풀며 넓히기" (2026-08-31)

사용자 제안: 최대 효율(목표 폭)로 **한 번에** 조여 전 조각이 겹친 상태를 만들고, 분리기가
풀지 못하면 폭을 조금씩 넓혀 가며 재분리한다 — 바깥→안이 아니라 **안→바깥** 궤적.
Egeblad(2007)·Umetani(2009) 계열의 고정 길이 겹침 최소화 + 길이 조정과 같은 발상이다.

엔진(`Separator::separate`)은 두 궤적이 같고 바깥 루프만 다르므로, 같은 시드·같은
예산에서 **최종 feasible 폭**을 나란히 놓으면 우열이 갈린다. 코어에는 이미 그 절반 —
폭 완화 복구 `ExplorationConfig::relief_*`(같은 폭에서 N번 실패하면 넓히며 재분리) —
가 있는데 **기본 꺼짐**이고 켠 실측이 없었다.

하네스 둘을 만들었다.

| 하네스 | 답하는 질문 | 노브 |
|---|---|---|
| `tests/target_width_jump.rs` | 점프 직후 한 번의 분리가 겹침을 얼마나 푸는가 · 넓히며 재분리해 닿는 feasible 폭 vs 같은 예산의 바깥→안 | `JUMP_TARGETS`(LBF 폭 대비 비율) `JUMP_SECS` `JUMP_WIDEN` `JUMP_SEEDS` |
| `tests/relief_sweep.rs` | 적응 탐색 노브(큰 걸음 `SWEEP_SHRINK`, 완화 `RELIEF_*`)를 켠 실제 파이프라인 최종 밀도. 팔 하나 = 호출 하나 | `SWEEP_SECS` `SWEEP_CMPR_SECS` `SWEEP_SEEDS` `SWEEP_SHRINK` `RELIEF_FAILS` `RELIEF_STEP` `RELIEF_MAX` `RELIEF_ROUNDS` `RELIEF_STRIKES` `RELIEF_ROUND_MS` |

기존 근거: fu(12조각)는 −15% 한 번 점프를 6초 안에 세 시드 전부 풀지만, shirts(99조각)는
−20% 를 안쪽 한도까지 못 푼다(`stop_latency` 가 그래서 그 설정을 쓴다). wsjk156 은
상용 밀도(82.28%)까지 −15.5% 가 필요하다. §4-4 계열 관찰 — 후반 실패 시도는 겹침의 95.8%
를 풀고 마지막 4% 에서 멈춘다 — 은 GLS 가 **작은 겹침 주입**에 맞춰진 기구임을 시사한다.

### 실측 A — 목표 폭 점프 (wsjk156, 팔마다 60s, 시드 3회)

| 팔 | 목표 폭 (밀도) | 진입 손실 | 60s 뒤 잔여 (해소율) | 결과 |
|---|---:|---:|---:|---|
| 바깥→안 (기준, 적응 탐색) | — | — | — | feasible **6635 / 6570 / 6597** (76.7 / 77.4 / 77.1%) |
| 점프 −5% | 6844 (74.3%) | 0.70~0.76M | **0 (100%)**, 4~8s | feasible 6844 / 6858 / 6830 — 기준보다 **넓다** |
| 점프 −10% | 6484 (78.5%) | 1.55~1.62M | 15k~61k (96~99%) | **미해소** |
| 점프 −16% (상용 82.28% 폭 근처) | 6052 (84.1%) | 2.48~2.71M | **510k~540k (80%)** | **미해소** — 멀다 |

세 시드가 같은 그림이다.

* **같은 60초에서 바깥→안이 이긴다.** −5% 점프는 4~8초 만에 풀리지만 거기서 멈추면
  74.3% 이고, 기준은 같은 시간에 76.7~77.4% 까지 내려간다(LBF 폭의 약 0.915배).
* **목표 폭(−16%)으로 점프하면 60초에 겹침의 80% 만 풀린다.** 잔여 손실이 −10% 팔의
  10~30배다. 전 조각이 겹친 상태에서 GLS 가 기울기를 잃는다는 §4-4 계열 관찰이
  156조각에서 그대로 재현됐다. shirts(99조각) −20% 미해소와 같은 결이다.
* −10% 는 경계다 — 96~99% 를 풀고 마지막 1~4% 에서 60초를 다 쓴다. 정확히 후반
  좁히기 실패의 모양("95.8% 풀고 멈춘다")이다.

**하네스 결함 하나** — 첫 분리에 예산 전체(60s)를 줘서 "넓히며 재분리" 반은 한 번도
돌지 못했다(`넓힘 0회`). 다음에 돌릴 때는 첫 분리에 예산의 일부(예: 1/3)만 주고
나머지를 넓히기 라운드에 남겨야 제안의 후반부가 측정된다.

### 실측 B — 큰 걸음 + 폭 완화 복구 A/B: **미실행**

사용자 요청으로 B1(기준) 시작 직후 중단했다. 명령은 §9-E 표의 노브로 그대로 돌린다:
`SWEEP_SECS=480 SWEEP_CMPR_SECS=120 SWEEP_SEEDS=0,1,2` 기준 팔과
`SWEEP_SHRINK=400 RELIEF_FAILS=2 RELIEF_ROUND_MS=2000` 팔, 각 30분.

### 판정 (부분)

"목표 폭에서 시작" 은 이 규모에서 **실현 가능성이 낮다** — 분리기가 대량 겹침을
못 푼다. 살아 있는 것은 "적당히 큰 점프(−5%~−10%) + 안 풀리면 넓히기" 조합인데,
그건 코어의 `relief_*` 가 이미 하는 일이라 **B 실험이 그 판정**이다.

### 조각 대응 (`tests/competitor_warm_start.rs`)

파일에 `item_id` 가 없고 정점이 단순화돼 있어(median 51 vs 179) 기하 해시는 안 맞는다.
이동 불변 특징 — 면적 · bbox 폭/높이 · 중심 2차 모멘트 `mu20/mu02/mu11` · bbox 중심
대비 무게중심 편이 — 로 탐욕 일대일 대응했다. 전역 미러 네 가설을 전부 시도해 총
불일치가 가장 작은 것을 고른다.

| 가설 | 총 불일치 | 최악 |
|---|---:|---:|
| 그대로 | 79.07 | 1.529 |
| y 반전 | 81.29 | 1.530 |
| x 반전 | 4.66 | 0.511 |
| **둘 다 (전역 180° 회전)** | **1.31** | **0.021** |

156/156 대응, 무게중심 정렬로 놓으면 폭 6182.88 / **82.28%** 가 파일값과 정확히
재현된다 — 좌표 해석이 맞다는 증거다.

**우리 CDE 로 보면 겹침이다**: 진입 손실 262,191. 우리 충돌 도형은 단순화로
x1.00098 부풀어 있고 상용은 median 0.187 mm 간격으로 맞물려 있으니 예상된 일이다.
규모로는 LBF 에서 약 −2% 점프한 정도다(−5% 점프의 진입 손실이 700k 대).
탐색의 첫 일이 이 해소이고, **첫 feasible 폭이 6183 근처인지 훨씬 넓은지**가
"우리 분리기가 그 품질의 해를 다룰 수 있는가" 의 첫 신호다.

### 실측 — 탐색 480s + 압축 120s, seed 0

```text
우리 CDE 로 본 상용 배치   배치 156/156  폭 6182.88  밀도 82.28%  진입 손실 262,191
탐색 480s   첫 feasible 폭 6182.88  최종 6182.88 (82.28%)  1개 개선
압축 120s   최종 폭 6182.88  밀도 82.28%
```

**"1개 개선" 은 개선이 아니다.** `exploration_phase_adaptive` 는 초기 해를 검사 없이
`feasible_sols` 에 넣는다(642행; loss==0 검사는 콜백 보고만 가른다). 즉 480초 동안
**feasible 해를 한 번도 못 찾았다.** 초기 분리가 안 풀리면 루프는 같은 폭에서 ALNS
교란·재분리만 반복하고 좁히지 않는다. 완화(`relief_*`)는 기본 꺼짐이고 폭 진동은
`best_width`(=출발 폭) 기준이라 넓히지도 못한다. 압축은 infeasible 출발이라 모든
시도가 자명하게 실패해 출발값을 돌려준다.

그러므로 이 결과는 "우리 탐색이 그 품질의 해를 망가뜨렸다" 가 **아니다.**
**우리 충돌 기하 정의(단순화 x1.00098 부풀림 + 좁은 오목부 메움)로는 상용 배치가
처음부터 실행 불가능**하고, 분리기가 그 262k 를 8분 동안 못 풀었다는 뜻이다.

이건 격차 해석을 바꾼다: 82.28% 가 **우리 feasible 집합 밖**이라면, 남은 격차의 일부는
탐색이 아니라 **기하 정의가 요구하는 여유**다. 그 크기는 아래 프로브가 잰다 —
폭을 +0.2 / +0.5 / +1.0% 넓혔을 때 우리 기준으로 풀리는 지점.

### 프로브 — 분리 단독, 각 120s (`WS_PROBE_SECS=120`)

| 폭 | 밀도 | 진입 손실 | 120s 뒤 잔여 (해소율) |
|---:|---:|---:|---:|
| x1.000 = 6182.88 | 82.28% | 262,191 | 20,437 (92.2%) |
| x1.002 = 6195.25 | 82.11% | 251,547 | 23,086 (90.8%) |
| x1.005 = 6213.80 | 81.87% | 254,166 | 9,671 (96.2%) |
| x1.010 = 6244.71 | 81.46% | 260,093 | 7,276 (97.2%) |

**폭을 1% 넓혀도 진입 손실이 거의 안 줄고(262k -> 260k) 120초로도 못 푼다.**
`change_strip_width` 는 조각을 옮기지 않으므로 이 손실은 거의 전부 **조각끼리의
겹침**이다 — 우리 충돌 도형이 단순화로 x1.00098 부풀어 있어(300mm 조각이면 변당
~0.15mm, 이웃 사이 ~0.3mm) 상용의 인접 간격(median 0.187mm)보다 크다.
**상용은 우리 충돌 기하가 표현할 수 없는 틈으로 맞물려 있다.**

§2-2(scale-collapse)의 "단순화 손실 0.1%p" 는 **면적** 손실이었다. 여기서 보이는 것은
**포장 가능성** 손실이다 — 부풀린 도형으로는 그 맞물림 자체가 불가능하다. 둘은 다른
양이고 후자가 훨씬 크다.

### 기하별 진입 손실 — **조건 차이의 정체는 sub-mm 공차다** (분리 단독 60s, x1.000)

| 기하 (`WS_GEOMETRY` / `WS_OVERLAP_MM`) | 진입 손실 | 60s 뒤 |
|---|---:|---|
| 기본 (단순화 x1.00098) | 262,191 | 잔여 20,437 — 미해소 |
| **정확** (단순화·오목부 메움 없음) | 132,487 | 잔여 32,074 (75.8%) — **여전히 미해소** |
| 기본 + **겹침 1mm** | 23,574 | **0 — 즉시 feasible (0s)** |
| 기본 + **겹침 2mm** | 29,968 | **0 — 즉시 feasible (0s)** |

정확 기하로도 겹침 0 조건에서는 실행 불가능하다 — 단순화 부풀림이 절반(262k -> 132k)을
설명하고, 나머지 절반은 **상용 배치 자체가 우리 원본 다각형 기준으로 sub-mm 파고들어
있기 때문**이다(플로터 출력 윤곽이 단순화돼 우리 원본보다 안쪽이고, 인접 간격 median
0.187mm 에 겹침 1.6mm² 가 이미 있다). 그리고 **승인된 1~2mm 공차를 주면 즉시 feasible**
이 된다.

> 격차 해석이 여기서 확정된다. 상용의 82.28% 는 **우리 기하 정의 + 겹침 0** 의 feasible
> 집합 밖이고, **겹침 1mm 이상** 의 feasible 집합 안이다. 우리가 겹침 2mm 로 얻은
> +1.55%p 는 "공차를 풀어 준 이득"이 아니라 **상용과 같은 조건으로 맞춘 것**이다.
> 남은 질문은 하나 — 같은 조건(겹침 2mm)에서 우리 탐색이 82.28% 를 넘는가(④).

(겹침 1mm 의 진입 손실이 2mm 보다 작은 것(23.6k < 30.0k)은 손실 프록시가 축소된 도형의
정점 구성에 비선형이라서다. 둘 다 0초에 풀리므로 판정에는 영향 없다.)

### ④ 겹침 2mm 에서 우리 탐색 — 480s + 120s, seed 0

```text
출발 (상용 배치)   폭 6182.82  82.28%   진입 손실 29,968 -> 0s 에 해소
탐색 480s          최종 6151.28  82.70%   4개 개선
압축 120s          최종 6143.78  82.80%
```

**우리 분리기는 그 품질의 해를 유지하고, 조금 더 좁힌다** (+0.52%p). 다만 8분에
개선 4개 — 상용 배치는 이 분리기의 고정점 바로 옆에 있다.

같은 조건(겹침 2mm)에서 우리 자신의 파이프라인은 LBF 출발로 **80.29%**(기본 걸음) /
**80.92%**(`shrink_step` 0.004)다. 즉:

> **격차 1.4~1.9%p 는 분리기의 천장이 아니다** — 분리기는 82.8% 를 다룬다.
> **우리가 LBF 에서 출발해서는 그 영역에 도달하지 못하는 것**이다. 격차는 탐색
> 엔진이 아니라 **출발 구조와 궤적**에 있다.

이것이 여러 실측을 한 줄로 묶는다.
* 시드 **폭**은 전달되지 않는다(§9-B, scale-collapse §2-4) — 그러나 시드 **구조**는
  전달된다: 오목도 정렬이 시드 −1.34%p 인데 최종 +0.71%p 였고, 상용 배치는 82.8% 로
  이어졌다.
* 설정 노브가 19전 1승인 이유 — 노브는 궤적의 속도를 바꾸지 도착 영역을 바꾸지 않는다.
* 목표 폭 점프가 안 되는 이유 — 겹침 덩어리에서는 구조가 생기지 않는다.

### 판정과 다음 방향

1. **공정 조건은 겹침 1~2mm 가 맞다.** 상용도 그 조건에서 만든 배치다. 겹침 0 에서
   82% 를 겨냥하는 것은 존재하지 않는 목표를 쫓는 것이다(정확 기하로도 실행 불가능).
2. **분리기·후처리는 손대지 않는다.** 82.8% 를 다룬다.
3. **남은 격차의 자리는 초기 구조다.** 상용 배치가 어떤 구조인지(`competitor_gap` 의
   구간 충전율: 최악 73.0% / 최고 89.2%, 약한 구간 없음)를 시드 목표로 삼아야 한다 —
   폭이 아니라 **탐색이 파고들 수 있는 맞물림 배열**을 만드는 초기 배치. 오목도 정렬이
   그 방향의 첫 증거(+0.71%p)이고, 상용 배치의 조각 배열 자체를 분석해 규칙을 뽑는 것이
   다음 작업이다(어느 조각이 왼쪽/아래에, 어떤 쌍이 맞물려 있나 — 대응표가 있으니
   조각 단위로 비교 가능하다).
4. 실용 운용점(코드 변경 없음): 겹침 2mm + `ShrinkStep` 0.004 + LBF "오목도부터".
   세 가지가 합쳐지는지는 아직 안 쟀다.

## 9-G. 상용 최종 배치의 구조 분석 → "선택(best-fit)" 가설 실측 — **기각** (2026-09-06)

### 배경

사용자 정정: 상용 최종 82.28%, 초기 배치는 좌표 없음. 눈으로 본 것은 **실행 3초에 77~78%**.
공차(1~2mm 겹침)로 우리 구성기를 돌려도 71~72% 라 공차는 답이 아니다(사용자 실측).
남은 후보를 최종 좌표(`data/reference/competitor_wsjk156.json`)의 구조에서 좁혔다.

### 구조 분석 (`tests/competitor_structure.rs`, 탐색 없음, 2.6s)

| 배치 | x~면적 | x~높이 | x~오목도 | 접촉비 | 동형이웃 |
|---|---|---|---|---|---|
| 상용 최종 82.28% | +0.33 | +0.17 | −0.03 | 5.3% | 17% |
| 우리 LBF 큰것부터 | −0.63 | −0.34 | −0.11 | 2.2% | 20% |
| 우리 LBF 오목도부터 | +0.09 | −0.35 | −0.94 | 3.6% | 16% |

(x~X = 조각 x 위치와 X 의 순위 상관. 접촉비 = 이웃 경계 0.5mm 안 둘레 비율. 동형이웃 = 동일 형상 그룹 쌍 중 간격<1mm 비율.)

* 상용은 면적·높이·오목도 어느 것과도 위치가 강하게 묶이지 않는다 → **고정 순서 구성이 아니다**.
* 동일 형상 묶음 없음(17% vs 20%). 접촉비는 2.4배지만 절댓값 5% 로 최적화 몫과 구분 불가.
* 남는 가설: 순서가 아니라 **선택** — 매 스텝 남은 조각 중 현재 경계에 가장 잘 맞는 조각+자리.

### 선택 가설은 이미 구현돼 있었다 — `initial/attach.rs` `Structure::Global`

N01/N02C 엔진의 `Structure::Global` 이 정확히 "미배치 전체 × 배치 전체 후보에서 전역 최선 1개"
(NFP 접촉점 후보 + 슬라이딩, 점수 = waste/area + len_gain/H + 좌하단). 2C-B 당시 Sorted 가
이겼다는 주석만 있고 수치가 없어 재측정했다. 추가한 노브(전부 `AttachCfg`, 기본값 = 기존 동작):

* `pool_window` — 정렬 상위 K 개 안에서만 선택 (0 = 전체, 1 = Sorted 와 동치)
* `select_size_bias` — 선택 점수에 `− bias · area/area_max` (작은 조각 편향 상쇄)
* `select_lbf_scale` — 선택 점수의 좌하단 항 배율 (0 = 맞춤 항만)
* 3b 선택 단계에서 **자리(j)는 배치 점수, 조각(s)은 선택 점수**로 분리

### 실측 (`tests/bestfit_probe.rs`, wsjk156, stage S2C, cap 32, seed 0/1/2 평균)

| 팔 | 시드 밀도 | 시간/회 |
|---|---|---|
| Sorted (큰 것부터, 기준) | **72.20%** | 2.6s |
| Global 순수 (기존 점수) | 64.37% | 22s |
| 창 3 / 6 / 12 / 24 (기존 점수) | 69.4 / 69.0 / 67.9 / 67.8% | 3–8s |
| Global, 맞춤 항만 (배율 0), 편향 0.3 / 1 / 3 / 10 / 30 | 69.2 / 66.5 / 68.4 / 68.0 / 69.6% | 19s |
| Global, 맞춤 항만, 편향 100 / 1000 (→ Sorted 수렴 확인) | 71.2 / 71.0% | 19s |
| 창 12, 맞춤 항만, 편향 1 | 69.3% | 5s |

편향을 키울수록 Sorted(71~72%)로 **단조 수렴**하고, 선택 비중을 늘리면 늘릴수록 나빠진다.
창·편향·배율 어느 조합도 Sorted 를 넘지 못했다(최선 69.9% vs 72.2%, 노이즈 ±0.4%p 밖).

### 판정

* **bbox 낭비 기준의 best-fit 선택은 이 인스턴스에서 시드 밀도를 올리지 못한다.** 가설 기각.
  상용의 "약한 크기 상관" 은 선택 방식의 서명이 아니라 3초 안에 들어 있는 짧은 국소
  압축(슬라이드/재배치)의 결과일 가능성이 더 크다.
* 남은 구성 단계 후보는 **맞춤 기준 자체**다: bbox 증가량이 아니라 조각 뒤에 남는 실제
  빈 면적(래스터 점유 기반 pocket 낭비). 이건 별도 작업(래스터 점유 + 후보 평가 교체)이고,
  시드 이득이 최종에 실리지 않는 함정(§9-B)이 그대로 남는다.
* 실용 운용점은 변함없다: 겹침 2mm + `ShrinkStep` 0.004 (+ 오목도 정렬은 wsjk156 한정).

### 후속 — 래스터 맞춤 기준 (`initial/raster.rs`, `AttachCfg::raster_fit_cell`) — **72% 벽 확인**

"틈을 보는 눈" 을 추가했다: 스트립 점유 래스터를 두고 후보 자리의 낭비를 bbox 증가량 대신
**bbox 안쪽 빈 칸 + 왼쪽/아래 그림자 빈 칸** 면적으로 센다. 노브 `raster_fit_cell`(mm, 0 = 끔),
`raster_shadow_cap`(칸). `try_push_placed` 성공 시 표시, 제거 경로는 미반영(S2C 프로브 용).

| 팔 (wsjk156, S2C, cap 32) | bbox 낭비 | 래스터 5mm |
|---|---|---|
| Sorted 큰 것부터 (3시드) | 72.20% | 72.00% |
| Global 맞춤 항만, 편향 1 (결정적) | 66.54% | **71.81%** (284s) |
| 창 12 맞춤 항만, 편향 1 (3시드) | 69.30% | 68.50% |
| Global 기존 점수 | 66.38% | 63.54% |

조율(시드 0, Global 결정적): 편향 0.3 / 3 → 66.2 / 70.2%, 그림자 상한 16 / 256 → 69.6 / 65.1%,
칸 3mm → Sorted 71.8 / Global 68.4%. 어느 조합도 71.81 을 넘지 못했다.

**판정.** 래스터 기준은 전역 선택을 66.5 → 71.8 로 살렸지만(기준이 실제로 작동한다는 증거)
정렬을 넘지 못했고, 정렬 자체는 기준을 바꿔도 그대로다. 순서·선택·평가 세 축을 모두 돌린 결과
구성 단계는 **72% 근처로 수렴**한다 — 사용자가 공차·순서 변경으로 확인한 71~72% 와 같은 벽이다.
상용의 3초 77~78% 는 이 계열의 구성 규칙으로는 설명되지 않는다. 구성 단계 축은 여기서 닫는다.
남는 설명은 구성 직후의 짧은 국소 압축(슬라이드·재배치)이며, 그건 초기 배치 좌표가 있어야 검증된다.

## 11. 업스트림 반영 (a2c10cc 이후) + jagua-rs 0.8.1 승급 (2026-09-06)

업스트림 swarm 는 `a2c10cc`(2026-09-01) 이후 커밋 13개 / 약 1,500줄이 쌓였다.
그중 1,250줄이 신규 TUI 이고 알고리즘 코드 변경은 6파일 29줄뿐이다. 대조 결과:

| 업스트림 변경 | 우리 상태 | 조치 |
|---|---|---|
| 로그 포맷 `{:.3}` -> `{}` (57c45cd) | 버그 있었음 | **적용** |
| `cd_threshold` 16 -> 64 (d271fd0) | 없음 | 미적용 (우리 인스턴스에선 무효) |

| itertools `array_combinations` | 이미 있음 | - |
| TUI 신규 | 없음 | 불필요 (WPF 사용) |

### 로그 포맷 버그 (적용)

`FMT().fmt2()` 는 문자열을 돌려주는데 `{:.3}` 을 붙이면 **세 글자로 잘린다**.
`1.23M` -> `1.2` 로 자릿수와 단위가 통째로 사라져 측정 로그를 오독하게 만든다.
`optimizer/explore.rs:112` 와 `optimizer/explore_mods.rs:755` 두 곳을 고쳤다.
업스트림은 앞의 것만 고쳤지만 우리는 뒤가 적응 탐색 경로라 함께 고쳐야 한다.

### `cd_threshold` 는 우리에게 무효 — 그리고 `quadtree_depth` 도 레버가 아니었다

`cd_threshold` 는 쿼드트리 하강을 멈추고 무차별 간선 검사로 넘어가는 임계값이며
탐지 결과를 바꾸지 않는 순수 성능 노브다. wsjk156 은 리프당 약 523 간선으로
34개 인스턴스 중 가장 조밀해서 16이든 64든 걸리지 않고 항상 리프까지 내려간다.
업스트림 값은 리프당 0.2~6 간선인 고전 벤치마크에 맞춘 것이다.

"그러면 `quadtree_depth` 를 올려야 한다"는 가설을 `tests/quadtree_depth_sweep.rs` 로 실측했다
(wsjk156, 탐색 120s + 압축 30s, 시드 0/1/2):

| depth | 최종 밀도 평균 | 탐색 개선 횟수 | LBF 시간 |
|---|---|---|---|
| 4 (현재) | 78.16% | 50.3 | 0.88s |
| 5 | 78.27% | 50.3 | 0.81s |
| 6 | 78.07% | 49.0 | 0.58s |

**기각.** 밀도 차이 0.20%p 는 노이즈 밴드(±0.4%p) 안이고, 결정적으로 **탐색 개선 횟수가
전혀 늘지 않았다**. 깊이를 올려도 분리기 처리량이 그대로라는 뜻이고, 분리기 병목이
충돌 검출 해상도가 아니라는 증거다. 실재하는 이득은 LBF 구성 34% 단축(0.88->0.58s)뿐인데
10분 예산에서 0.3초는 0.05% 라 기본값을 바꿀 근거가 못 된다. **깊이 4 유지.**
다만 구성 단계가 지배적인 경로(`initial/` 엔진, 다중 시작)에서는 깊이 6 이 검토 대상이다.

### jagua-rs 0.7.2 -> 0.8.1 (적용)

앞선 조사에서 "31커밋의 API 변화가 우리 충돌 파이프라인을 직접 때린다"고 봤으나
**과대평가였다.** 실제 제거된 공개 API 는 하나뿐이다.

* `HazardCollector` 트레잇은 두 버전이 **완전히 동일** — 우리 `SpecializedHazardCollector` 무수정.
* `collect_poly_collisions` / `collect_collisions` 는 이름이 바뀐 게 아니라 `_until` 변형이 **추가**됐다.
* `detect_surrogate_collision` 시그니처 그대로. 시그니처가 바뀐 `collect_surrogate_collisions` 는 우리가 안 쓴다.
* 우리 `CDEConfig` 는 세 필드를 모두 명시하므로 상류 기본값 변경에 영향 없다.

고친 곳은 두 종류뿐이다.

1. **`n_ff_poles: 1` -> `ff_pole_area_ratio: 0.001`** (6곳: config.rs + nfp_strategy 4 + nfp_sampler).
   0.8 은 fail-fast 폴을 개수가 아니라 **면적 비율**로 고른다 —
   `target = poly.area * ratio` 를 큰 폴부터 누적해 넘는 지점까지 채택한다.
   첫 폴(최대 내접원)은 항상 채택되므로 비율을 첫 폴의 면적 비중보다 작게 두면
   정확히 1개가 뽑혀 기존 동작과 같다. 우리 조각은 가장 가는 것도 내접원이 면적의 수 % 라
   0.001 은 안전 마진이 크다. **업스트림 기본은 0.5 지만 그건 훨씬 공격적인 fail-fast 이므로
   승급을 동작 중립으로 유지하려고 기존 동작을 보존했다. 0.5 는 별도 노브로 재야 한다.**
2. **`SecondaryMap::new()` -> `BasicHazardCollector::new()`** (2곳: optimizer/explore.rs, src/ffi_step.rs).
   0.8 에서 `BasicHazardCollector` 가 타입 별칭에서 구조체가 되어 `SecondaryMap` 이
   더 이상 `HazardCollector` 가 아니다. 우리가 쓰는 `new()`/`with_capacity()` 는 그대로 있다.

**동작 중립 검증** (같은 조건 재측정):

| | 최종 밀도 평균 | 탐색 개선 횟수 | LBF 시간 |
|---|---|---|---|
| 0.7.2 (승급 전) | 78.16% | 50.3 | 0.88s |
| 0.8.1 (승급 후) | **78.19%** | 49.7 | **0.67s** |

밀도 차 0.03%p 로 노이즈 안. 덤으로 LBF 구성이 24% 빨라졌다(0.88 -> 0.67s).

**테스트**: 라이브러리 94개 통과. `tests/grouped_ffi.rs` 3개가 실패하지만
승급을 되돌려 0.7.2 에서 돌려도 **동일하게 실패**한다 — 기존 실패이고 이번 작업과 무관하다
(콜백 스트리밍 타이밍 관련, 별도 사안). C# 69개 통과, `EnsureCompatible()` 통과.

### 커스텀 파이프라인 vs 0.8.1 네이티브 — 4단계 계획 실측, **네이티브 전환 기각** (2026-09-06)

상류 swarm 0.2.0 은 커스텀 충돌 파이프라인을 버리고 jagua 네이티브
`collect_*_until` 로 갈아탔다. 우리도 가야 하는지 **한 번에 한 노브씩** 실측했다.
기준선은 jagua 0.8.1 승급 직후 상태(wsjk156, 탐색 120s + 압축 30s, 3시드).

| 단계 | 내용 | 최종 밀도 | 판정 |
|---|---|---|---|
| 1 | `ff_pole_area_ratio` 0.001 → 0.5 | 78.15 → 78.27% | **채택** (노이즈 안) |
| 2 | bounded SIMD 조기 종료 이식 | 동작 무변경 | **채택** (순수 추가) |
| 3 | 엣지 순회 비트 반전 → 인덱스 순서 | 78.19 → 77.80% | **기각** |
| 4 | 파이프라인 네이티브 교체 | — | **기각** (3단계가 전제를 무너뜨림) |

#### 1단계 — `ff_pole_area_ratio` 0.5 채택

0.5 는 (a) 상류 기본값, (b) 네이티브 전환이 강제하는 값, (c) 우리 분리기 핫루프가
이미 하드코딩해 쓰는 "면적 50%" 규칙과 같은 값이다. 실측이 노이즈 안이라 채택했다.
프로덕션 1곳 + 테스트 픽스처 5곳 모두 변경.

#### 2단계 — bounded SIMD: 교체가 아니라 **추가**

여기서 중요한 사실이 드러났다. **우리 SIMD 가 상류보다 앞서 있다.**

* 우리는 런타임에 CPU 를 보고 AVX-512(16폭) → AVX2(8폭) → SSE(4폭) 를 고른다.
  상류는 `SIMD_WIDTH = 4` 고정이다.
* 우리에겐 `pd <= 0` 클램프가 있다. 상류는 침투 깊이가 음수일 때도 양수 감쇠를
  돌려준다 — **우리가 고친 버그가 상류에 그대로 남아 있다.**
* 우리 `debug_assert!(is_finite && >= 0.0)` 가 상류의 `is_normal()` 보다 정확하다
  (겹침이 정확히 0 이면 `is_normal()` 은 거짓이다).

그래서 상류 코드로 갈아타지 않고 **우리 커널에 조기 종료만 얹었다**:
`poles_overlap_area_proxy_simd_bounded` / `quantify_collision_poly_poly_simd_bounded`.
상한 검사는 `sp1` 폴 하나를 끝낼 때마다 한 번 — 청크마다 검사하면 분기 비용이 SIMD
이득을 깎는다. 누적값이 단조 증가라 한 번 넘으면 내려올 수 없어 조기 탈출이 안전하다.
상한은 최종 손실에서 "PI 곱하기 전" 단위로 역산해 넘긴다(커널이 PI 를 안에서 곱한다).
테스트 4개로 못 박았다(`quantify::simd::bounded_tests`).

**주의: 아직 아무도 호출하지 않는다.** 실제로 쓰려면 분리기의 손실 상한을 커널까지
연결해야 한다 — 지금은 쌍 하나를 끝까지 정량화한 뒤 바깥에서 버린다. 순수 속도
개선이고 결과를 바꾸지 않으므로 다음 후보로 안전하다.

#### 3단계 — 엣지 순회 순서: 비트 반전 유지

| 순회 | 최종 밀도 | 탐색 개선 횟수 |
|---|---|---|
| 비트 반전 (우리) | 78.27% / 78.10% (2회) | 50.0 / 49.7 |
| 인덱스 순서 (상류·네이티브) | 77.80% | 46.7 |

**해석 주의.** 기준선을 두 번 재니 78.27% 와 78.10% 로 0.17%p 흔들렸다. 따라서 밀도
차이는 0.39%p 로 ±0.4%p **밴드 경계**이지 밴드 밖이 아니다. 더 분명한 신호는 처리량이다:

| 시드 | 비트 반전 | 인덱스 순서 |
|---|---|---|
| 0 | 49, 49 | 49 (동일) |
| 1 | 52, 51 | 46 (감소) |
| 2 | 49, 49 | 45 (감소) |

3시드 중 2개에서 처리량이 떨어지고, 밀도가 낮아진 시드도 정확히 그 둘이다.
기전이 일관된다 — 조기 종료가 덜 걸려 같은 예산에 분리 반복을 덜 돈다.
비트 반전이 나쁠 이유가 없고 2/3 에서 낫다. **유지.**

#### 4단계 — 네이티브 교체 기각

네이티브는 `shape.edge_iter()`, 즉 인덱스 순서를 쓴다. 3단계가 그 순서의 비용을
측정했으므로 선택지는 둘뿐이다.

* 그대로 갈아탄다 → 처리량을 잃는다
* 비트 반전을 들고 간다 → 그건 갈아타는 게 아니라 우리 파이프라인 유지다

네이티브의 유일한 실익이던 조기 종료는 이미 우리가 갖고 있고(커스텀 파이프라인),
2단계로 SIMD 정량화에도 상한을 넣었다. 남는 차이는 전부 우리가 **더 나은** 쪽이었다.
**커스텀 파이프라인을 유지한다.**

**조각끼리는 겹치지 않았다.** 문제는 `poly_simpl_tolerance: 0.001` 이 충돌 도형을
최대 0.9mm 부풀리는 것이다. 상용 마커는 조각이 원단 폭 1524mm 에 정확히 꽉 차 있어
부풀린 도형이 곧바로 경계를 넘는다. 이것은 **분리기로 고칠 수 없다** — 도형이 원단보다
큰 것이라 밀어 넣을 자리 자체가 없다.

겹침 허용을 키우는 것도 답이 아니다. 0.2mm 에서 오히려 실패한다 —
겹침 허용은 아이템을 X/2 줄이면서 **컨테이너도 X/2 줄이므로**(원단 가장자리를 닫아
두려는 우리 수정) 가장자리 조각이 밖으로 나간다. 동작 창이 0.1mm 로 좁다.

#### 조치

1. **WPF 가 Use Hints 켜짐 + 힌트 있음일 때 설정을 맞춘다**
   (`WorkspaceViewModel.RunPipelineAsync`). PolySimpl 이 0 이상이면 끄고, 겹침 허용이
   0 이면 `HintPieceOverlapMm = 0.1` 을 넣는다. **사용자가 직접 정한 값은 건드리지
   않고**, 보정한 사실과 이유를 실행 로그에 남긴다.
2. **미세 겹침은 버리지 않고 그 자리에서 푼다** (`legacy_seed_problem_separated`).
   좌표는 그대로 두고 분리기로 겹침만 해소한다 — 상용 배치의 **구조**가 보존된다.
   경계 검사는 유지한다(위 이유로 분리기가 못 고치는 사안에 10초를 낭비하지 않는다).
   frozen 힌트가 있으면 쓰지 않는다(분리기는 고정 여부를 모른다).
3. **복구된 시드에는 warm start 자격을 주지 않는다** (`seed_was_repaired`).
   좌표는 사용자 것이지만 우리가 손댄 배치이므로 Structure P1 을 건너뛰는 지름길은
   손대지 않은 시드에만 열려 있어야 한다. 기존 계약
   (`legacy_init_repairs_overlapping_movable_hints`,
   `discarded_movable_seed_runs_structure_p1_instead_of_warm_start_shortcut`)이 그대로 산다.
4. **폴백을 시끄럽게 만든다.** 예전에는 조용히 LBF 로 떨어져 사용자가 이유를 알 수 없었다.
   이제 버린 힌트 수·사유와 함께 "경계 위반이면 PolySimpl 을 끄고, 조각 겹침이면
   Piece Overlap 을 관통 깊이보다 크게" 라는 조치를 로그에 남긴다.

#### 검증

`tests/hint_warm_start.rs` 4개. 합성 인스턴스로 (a) 깨끗한 힌트가 그대로 쓰이는지,
(b) 미세 겹침이 버려지지 않고 복구되는지, (c) 힌트가 없으면 예전대로 LBF 가 도는지를
고정하고, (d) `HINT_JSON` 이 주어지면 실제 상용 마커 변환본으로 확인한다 —
**156개 배치, 폭 6456.2, 밀도 78.79%** 로 상용 배치가 그대로 초기 해가 된다.

진단용 `swarm-core/tests/hint_feasibility.rs` 는 어느 설정 조합이 통과하는지
찾아 주는 하네스다(`HINT_JSON` / `HINT_OVERLAPS` / `HINT_SIMPL=off`).
