## 3. 우선 적용을 검토할 코드 최적화

### 우선순위 1: 회전별 폴리곤 경계 재사용

한 조각을 검색할 때 `search_impl`은 주변 샘플러와 전역 샘플러를 각각 만든다. 두 샘플러의 생성자는 같은 조각을 복사하고, 같은 허용 회전마다 형상을 변환해서 경계 상자를 다시 구한다.

주변 검색과 전역 검색에서 다른 것은 위치를 뽑을 범위다. **조각을 각 각도로 돌렸을 때의 형상 경계는 재사용할 수 있다.** 같은 조각을 다음 라운드에서 다시 검색할 때도 기하와 허용 회전이 같으면 동일한 준비가 반복된다.

제안:

1. 검색 한 번 안에서 회전별 형상 경계를 한 번만 만들고 두 샘플러가 공유한다.
2. 이득이 확인되면 불변 입력 형상과 회전 집합에 연결된 캐시로 수명을 늘린다.
3. strip 길이와 주변 검색 범위에 따른 유효 이동 구간은 매번 새로 계산한다.

현재 폴리곤 변환과 같은 산술 순서로 경계를 만들어야 한다. 원래 AABB의 네 모서리만 회전하는 대체 계산은 실제 회전 폴리곤의 AABB와 다를 수 있다. 회전 목록 순서, 중복 각도, 난수 소비 순서도 보존한다. 기하·간격·겹침 전처리 또는 허용 회전이 바뀌면 캐시를 새로 만들어야 한다.

장점은 탐색 전략을 바꾸지 않고 중복 준비를 제거할 수 있다는 점이다. 속도 이득의 크기는 별도 측정이 필요하다.

### 우선순위 2: 충돌 쌍의 형상 상수 재사용

폴리곤끼리 loss를 계산할 때 지름에 따른 epsilon과 convex hull 면적에 따른 penalty를 계산한다. penalty에는 두 면적의 제곱근과 곱의 제곱근이 들어간다. bounded SIMD 경로에서도 이러한 준비가 반복된다.

형상이 고정된 상태에서 평행 이동·회전만 수행한다면 이 값들은 수학적으로 변하지 않는다. **조각별 또는 조각 쌍별 상수로 준비하는 방식**을 검토할 가치가 있다.

단, 적용 전 다음 조건이 필요하다.

- 실제 형상 변환 구현에서도 해당 저장값이 동일하게 유지되는지 확인한다.
- 기존 f32 연산 순서로 계산한 값을 저장한다. 근사 제곱근이나 연산 재배열로 바꾸지 않는다.
- 반복마다 바뀌는 GLS 가중치와 후보별 loss 상한은 캐시에 포함하지 않는다.
- 모든 조각 쌍을 저장하면 O(N²) 메모리가 든다. 조각별 상수부터 재사용하는 방식과 비교한다.
- fat LTO가 이미 일부 계산을 이동·통합하는지 확인한다. 소스의 반복식 개수가 실행 비용과 항상 같지는 않다.

근거: [형상 penalty](C:/Caplanet/AiWorks/AdaptiveAlgorithm2/swarm-core/src/quantify/mod.rs:28), [bounded SIMD 평가](C:/Caplanet/AiWorks/AdaptiveAlgorithm2/swarm-core/src/quantify/simd/mod.rs).

### 우선순위 3: 같은 검색 안의 중복 좌표 평가 줄이기

좌표 하강 탐색에서는 양방향 후보를 반복 평가한다. 회전 제한에 걸리거나 부동소수점 이동량이 작으면 같은 좌표·각도가 다시 만들어질 여지가 있다. **현재 입력에서 얼마나 반복되는지는 아직 측정하지 않았다.**

먼저 한 검색 안에서 좌표·각도의 비트가 완전히 같은 후보의 비율을 측정한다. 적중률이 충분한 경우에만 작은 검색 전용 캐시를 검토한다.

주의점:

- 평가에는 ‘정확한 loss 계산 완료’와 ‘현재 상한을 넘어서 중간에 거부’가 있다. 거부 결과를 정확한 loss처럼 저장하면 안 된다.
- 상한 B에서 거부한 결과는 더 엄격한 상한에는 활용할 수 있지만, 더 느슨한 상한에서 그대로 거부하면 안 된다.
- CD의 1,000회 평가 한도가 `n_evals()`에 연결돼 있다. 캐시 적중 때 이 값을 세지 않으면 탐색 예산과 경로가 달라진다. 논리적 평가 횟수와 실제 계산 횟수를 구분해야 한다.
- 캐시 수명은 동일 조각·배치·가중치의 검색 안으로 제한한다. 다른 배치나 라운드로 무조건 재사용하지 않는다.
- 가까운 좌표를 같은 것으로 처리하는 양자화는 정밀도를 바꾸므로 제안하지 않는다.

이는 이전 A 실험의 ‘같은 위치 remove/place 생략’과 다른 변경이다. 그 실험이 실패했다고 후보 평가 캐시까지 불가능한 것은 아니지만, 안전하다는 근거도 아직 없다.

### 후순위: 워커 복사·임시 메모리 줄이기

현재 워커는 라운드 시작 때 배치를 복원하고 tracker를 복사한다. pair matrix는 이미 `Arc`로 공유되지만, 처음 수정할 때 `Arc::make_mut`가 행렬을 분리 복사한다. 승자 배치의 전달도 이미 `swap`으로 최적화돼 있다.

따라서 ‘Arc를 쓰자’, ‘승자를 swap하자’는 새 제안이 아니다. 추가 검토 대상은 다음과 같다.

- 라운드별 통계 목록, 검색별 임시 벡터, 변 인덱스 벡터의 할당 재사용.
- 잠금·그룹 메타데이터가 실제 바뀌었을 때만 갱신하도록 변경 버전 도입.
- COW 첫 쓰기의 할당·복사 시간을 계측하고, 영향이 클 때만 행 또는 블록 단위 분리 검토.

전체 행렬 복사를 줄이는 대신 모든 조회가 느려지면 손해다. 배치 복원을 일부 이동만 재생하는 방식으로 바꾸는 것도 배치 키의 세대, quadtree, strip 변경, 잠금 형상을 함께 일치시켜야 하므로 큰 변경에 해당한다.

## 4. 한 후보의 분리가 오래 걸리는 로직

현재 `separate()`의 반복 제어는 다음과 같다.

- loss가 0이면 성공한다.
- 이전 최저 loss보다 2% 넘게 좋아지면 ‘개선 없음’ 카운터를 0으로 만든다.
- 최저 loss가 조금 좋아지지만 2% 기준에는 못 미치면, 최선 배치를 저장하면서 카운터는 그대로 둔다.
- 최저 loss가 좋아지지 않은 반복에서만 카운터를 증가시킨다.

따라서 **아주 작은 개선이 계속 이어지는 후보는 카운터를 소모하지 않고 오래 실행될 수 있다.** strike도 충분한 개선이 있으면 초기화된다. 전체 시간 제한과 중지 확인이 있으므로 이를 무한 루프 버그로 판정하지는 않는다. 다만 사용자가 느끼는 ‘어려운 후보를 너무 오래 붙잡음’과 직접 관련된 로직이다.

개선 후보는 절대 loss 값으로 일괄 중단하는 방식보다, 일정 구간에서의 상대 개선량·실제 계산량·경과 시간을 함께 보고 한 후보에 줄 작업량을 배분하는 방식이다. `[SEP] min_l`은 조각 크기와 형상에 영향받는 휴리스틱 비용이므로, mm처럼 공통 임계값으로 자르면 안 된다.

이 변경은 검색 경로를 바꾼다. 늦게 성공할 후보를 너무 일찍 포기하면 최종 수율이 떨어진다. 시험한다면 해당 후보의 최저 loss 상태를 보존하고, 공개 결과는 마지막 정밀 인증 배치를 유지해야 한다. Config의 반복 제한을 단순히 낮추는 대안은 제안하지 않는다.

## 5. 병렬 처리 향상 여지

### 현재 대기가 발생하는 이유

`move_items_multi()`는 모든 워커가 해당 라운드를 마칠 때까지 기다린 다음 최소 가중 loss인 배치를 고른다. 먼저 끝난 워커의 결과를 즉시 채택하면, 아직 실행 중인 워커가 더 좋은 배치를 만들 가능성을 포기하게 된다. 이는 동기화 비용만 제거하는 변경이 아니라 선택 알고리즘 변경이다.

이전 20초·3시드 시험에서 ‘독립 Explore 3개 + 분리 완료 시 공통 최선 배치 인계’는 기존 동기식 대비 WSjk 평균 길이 +74.047mm, OPS2 +5.765mm였다. 이 시제품을 현재 동기식의 대체로 추천할 근거는 없다. 반대로 모든 비동기 방식이 불리하다는 증명도 아니다.

| 병렬화 후보 | 판단 | 이유 |
|---|---|---|
| 조각별 불변 회전 경계 준비 | 조건부 가능 | 서로 독립적이다. 우선 중복 자체를 제거하고, 초기 준비량이 클 때만 병렬화 |
| CD 양방향 후보 2개 동시 평가 | 우선순위 낮음 | 별도 평가 버퍼와 결과 순서 보존이 필요. 후보당 작업이 짧으면 스케줄링 비용이 더 큼 |
| 무작위 후보 묶음 동시 평가 | 실험 대상으로 한정 | 순차 평가 중 갱신되는 best 상한을 즉시 공유하기 어렵고, 느슨한 상한으로 불필요한 계산이 늘 수 있음 |
| 조각 이동을 서로 독립적으로 동시 채택 | 위험 | 한 조각 이동이 다른 조각의 충돌 조건을 바꿈. 검사 당시 유효한 이동들도 함께 적용하면 충돌 가능 |
| 원본 정밀 검사 작업 분배 개선 | 후순위 가능 | 이미 조건부 병렬화돼 있음. 복잡한 폴리곤 쌍의 작업 편차를 줄일 여지는 있음 |
| 독립 Explore 스트림으로 전면 교체 | 현재 비추천 | 앞선 시험에서 품질 손실. 사용자 승인한 동기식 유지와도 다름 |

## 6. SIMD 및 이미 적용된 최적화

후보 loss 계산은 이미 SoA 입력과 SIMD를 사용하며, CPU에 따라 AVX-512·AVX2 등의 경로를 선택한다. 상한을 넘으면 pole 계산 도중 조기 종료한다. 새로 SIMD를 도입하는 단계가 아니다.

추가 검토 방향은 다음과 같다.

- SIMD에 들어가기 전의 형상 상수 계산 및 입력 준비 중복 제거.
- CPU 경로 선택을 검색 시작으로 이동할 가치가 있는지 측정. CPU 기능 검사 자체는 캐시되므로 매번 CPUID를 실행한다고 해석하지 않는다.
- pole 쌍 수, 실제 SIMD 처리량, 상한 조기 종료 위치를 계측해 산술 병목과 메모리 병목을 구분.

가장 넓은 SIMD를 무조건 강제하거나 근사 sqrt로 바꾸는 방식은 추천하지 않는다. lane 합산 순서와 반올림이 바뀌면 상한 판정 및 탐색 선택이 달라질 수 있다.

변 검사 순서 재사용, 승자 상태 swap, pair matrix COW, 콜백·rollback 스냅샷 공유, 성공 인증 캐시, 원본 검사 캐시는 이미 존재한다. 새 최적화 성과로 중복해서 계산하면 안 된다. 콜백도 FFI 경로에 따라 전체 보고 또는 JSON만 제한하는 처리가 있으므로, 호출마다 전체 JSON을 생성한다고 가정해서는 안 된다.

## 8. 적응형 shrinkStep의 현재 동작과 개선 여지

### 8.1 shrinkStep은 무엇을 줄이는 값인가

`shrink_step`은 폴리곤의 크기나 조각의 이동 간격이 아니라 **다음에 도전할 strip 길이를 줄이는 비율**이다. 코드의 `width`는 여기서 원단 사용 길이에 해당한다.

현재 adaptive Explore에서는 충돌이 풀리고 결과 인증까지 통과한 뒤 다음 목표 길이를 정한다.

```text
실효 축소 비율 = base_step × 밀도 배율 × 실패 피드백 배율
다음 목표 길이 = 현재 길이 × (1 − 실효 축소 비율)
```

`base_step`은 기존 `shrink_step`이며, 실행 중 조절값이 있으면 그 값을 읽는다. `0.001`은 0.1%다. 밀도 배율 등이 1이면 6,500mm에서 6.5mm를 줄인다. 잠금에 따른 축소 하한도 적용한다.

중요하게도 **분리기 내부에서 min_l이 내려갈 때마다 strip을 계속 줄이지는 않는다.** 해당 목표 길이의 분리를 마친 뒤, 성공한 분기에서 다음 축소 비율을 계산한다. 실패 시에는 같은 길이에서 교란·재시도하거나 별도의 폭 진동/완화 복구를 수행한다.

근거: [성공 인증과 다음 길이 계산](C:/Caplanet/AiWorks/AdaptiveAlgorithm2/swarm-core/src/optimizer/explore_mods.rs:734), [실행 중 base_step 적용](C:/Caplanet/AiWorks/AdaptiveAlgorithm2/swarm-core/src/optimizer/explore_mods.rs:795).

### 8.2 지금 실제로 연결된 모드

Rust 코어에는 다음 다섯 모드가 있다.

| 모드 | 밀도 배율 | 실패 피드백 |
|---|---|---|
| Fixed | 1 | 없음 |
| DensityLegacy | `clamp(1 + gain × (1 − density), 1, max_mult)` | 없음 |
| DensitySlack | 시작 밀도로 정규화한 진행도에 따라 max_mult에서 1로 감소 | 없음 |
| Feedback | 1 | 실패 시 감소, 성공 시 회복 |
| DensitySlackFeedback | DensitySlack과 동일 | 실패 시 감소, 성공 시 회복 |

**현재 코어 기본값은 DensityLegacy이고, 현재 C ABI 변환도 모드를 이 기본값으로 지정한다.** C ABI에는 모드 선택 필드가 없다. WPF Sample에서 adaptive Explore 경로를 실행할 경우 이 연결을 따라간다. Rust에 Feedback 모드가 있다는 사실과 WPF 실행에 실패 피드백이 적용된다는 주장은 다르다.

WPF에는 `ShrinkFailDecay` 입력값이 있지만, 현재 모드의 `uses_feedback()`가 false라면 이 값만 바꿔도 피드백이 켜지지 않는다. UI 기본값은 1.0이고 Rust의 피드백 기본 계수는 0.6이다. 이번에는 설정을 바꾸거나 ABI를 확장하지 않았다. 실행 중인 별도 바이너리의 설정을 조회한 것도 아니며, 이 설명은 현재 체크아웃의 연결에 근거한다.

### 8.3 현재 방식도 밀도가 높아지면 step이 작아진다

기본 gain=4, max_mult=5일 때 DensityLegacy는 아래처럼 동작한다. 길이 변화와 배율의 영향을 구분하기 위해 6,500mm를 고정한 산술 비교다. 한 실행의 실제 밀도·길이 이력을 재현한 표는 아니다.

| 밀도 | 배율 | base_step=0.001의 실효 비율 | 6,500mm에서 줄이는 길이 |
|---:|---:|---:|---:|
| 60% | 2.60 | 0.260% | 16.90mm |
| 78% | 1.88 | 0.188% | 12.22mm |
| 80% | 1.80 | 0.180% | 11.70mm |
| 85% | 1.60 | 0.160% | 10.40mm |
| 90% | 1.40 | 0.140% | 9.10mm |

따라서 ‘처음 크게, 나중에 작게’라는 성격은 일부 존재한다. 하지만 **시간 경과, 최근 성공률, 분리에 든 비용을 기준으로 작아지는 방식은 아니다.** 밀도가 78%에서 거의 개선되지 않으면 배율도 약 1.88 근처에 머문다. 시간이 많이 남지 않았다고 자동으로 미세 축소 모드로 전환하지 않는다.

DensitySlack은 이를 시작 밀도 기준으로 바꾼다.

```text
p = clamp((현재 밀도 − 시작 밀도) / (1 − 시작 밀도), 0, 1)
배율 = 1 + (max_mult − 1) × (1 − p)^gain
```

예를 들어 시작 밀도 80%, gain=4, max_mult=5이면 배율은 시작에서 5, 밀도 85%에서 약 2.266, 90%에서 1.25다. 초기 5배가 이미 잘 배치된 입력에는 과할 수도 있다. 또한 100%를 진행도의 기준점으로 삼지만 실제 달성 가능한 수율이 그보다 낮을 수 있고, 겹침 허용 및 밀도에 쓰는 기하 때문에 이를 정확한 물리적 한계로 해석해서도 안 된다.

문서상 불일치도 확인했다. `config.rs`의 DensitySlack 주석에는 gain이 클수록 ‘초반을 오래 유지하다 급히 꺾인다’고 쓰여 있으나, 실제 식 `(1 − p)^gain`은 **gain이 클수록 같은 양의 p에서 더 빨리 감소**한다. 향후 정리할 설명 오류이며, 이번에는 Rust 주석을 수정하지 않았다.

### 8.4 기존 실패 피드백의 중요한 한계

Feedback 계열 모드에서는 한 목표 길이의 첫 실패에만 `scale *= decay`를 적용한다. 같은 길이에서의 반복 실패마다 곱하지는 않는다. 성공하면 다음 축소 전에 `scale /= decay`로 회복한다.

scale=1, decay=0.6에서, 폭 진동·완화 없이 같은 목표 길이에 머문 경우를 보면 다음과 같다.

```text
큰 축소 시도 → 첫 분리 실패 → scale=0.6
같은 목표 길이에서 계속 재시도 → scale=0.6 유지
결국 성공 → 다음 축소 직전에 scale=1로 회복
```

이 경로에서는 **한 번 실패했다가 성공한 경험이 다음 축소에 남지 않는다.** 더구나 scale을 낮춘 순간 현재 목표 strip이 넓어지는 것도 아니다. 현재 어려운 목표의 분리 시간을 직접 줄이는 조치는 아니다. 폭이 바뀌는 다른 복구 경로에서는 배율 이력이 달라질 수 있으므로 모든 경우에 피드백이 무효라고 단정하지는 않는다.

따라서 ‘너무 큰 축소를 실패하면 더 작은 축소를 실제로 다시 시도’하려면 배율 계산뿐 아니라 **목표 길이 재설정과 기준 배치 복원**을 함께 설계해야 한다. 이 부분이 단순 모드 변경보다 중요한 개선 지점이다.

근거: [성공 시 회복](C:/Caplanet/AiWorks/AdaptiveAlgorithm2/swarm-core/src/optimizer/explore_mods.rs:786), [첫 실패에서만 감쇠](C:/Caplanet/AiWorks/AdaptiveAlgorithm2/swarm-core/src/optimizer/explore_mods.rs:865).

### 8.5 `min_l: 83.1 K`를 기준으로 삼아도 되는가

`83.1 K`는 약 83,100이라는 검색용 최저 loss의 축약 표시다. 83.1mm 겹침이나 충돌 83,100쌍을 뜻하지 않는다. 형상 크기, 충돌 쌍, 원단 이탈 등 여러 요소가 반영된다. 로그의 min_l은 해당 분리 호출에서의 최저 raw loss이며, 워커 승자 선택에 쓰는 가중 loss와도 구분해야 한다.

**절대 min_l을 shrinkStep의 공통 기준으로 쓰는 것은 비추천이다.** ‘80K가 넘으면 절반으로 줄이기’처럼 적용하면 입력 크기와 조각 수에 따라 전혀 다른 판단을 한다.

| 신호 | 활용 적합성 | 해석상 주의 |
|---|---|---|
| 절대 min_l | 낮음 | 다른 입력·다른 목표 길이끼리 직접 비교 어려움 |
| 같은 목표의 `현재 최저 loss / 시작 loss` | 보조 신호로 적합 | 시작 loss가 0에 가까운 경우 방어, 교란·목표 변경 시 기준 갱신 필요 |
| 최근 일정 작업량당 상대 loss 감소 | 정체 판정에 유용 | 빠르게 감소해도 정밀 인증 성공을 보장하지 않음 |
| 정밀 인증된 축소 성공 여부 | 주요 신호 | 탐색용 loss=0만으로 성공 처리하지 않음 |
| 성공까지의 평가 수·경과 시간·재시도 수 | 주요 신호 | Stop·전체 마감으로 끊긴 시도를 일반 실패처럼 학습하지 않음 |
| 남은 Explore 시간 | 후반 step 상한에 유용 | 이것만 쓰면 쉬운 입력에서도 너무 일찍 소극적으로 변할 수 있음 |
| 밀도 | 초기 규모를 정하는 보조 신호 | 해당 입력에서 실제로 남은 개선 여유와 같지 않음 |

특히 GLS 가중 loss는 가중치 갱신 자체로 바뀐다. 시간에 따른 개선률을 볼 때 raw loss와 혼용하면 안 된다. 충돌 쌍 수를 신호로 추가한다면 이를 얻기 위해 매 후보마다 비싼 전체 스캔을 추가하지 않아야 한다.

### 8.6 추천: 초기에는 큰 축소를 허용하고, 난이도 피드백과 남은 시간으로 제한

사용자의 방향은 타당한 실험 후보다. 다만 시간을 따라 무조건 일정하게 줄이는 단독 방식보다는 다음 결합을 추천한다.

1. **초반:** 현재 밀도 기반 제안값을 출발점으로 사용한다. 빠른 인증 성공이 이어질 때만 큰 축소를 허용한다. 시작부터 최대 배율을 강제하지 않는다.
2. **난도가 올라간 경우:** 분리에 많은 작업이 들거나 자연 종료한 실패가 발생하면 축소량을 줄인다. 한 번 성공했다고 이전 실패 감쇠를 곧바로 전부 회복하지 않는다. 여러 번의 빠른 성공 후 천천히 회복한다.
3. **후반:** 남은 시간에 따라 허용할 step의 상한을 낮춘다. 쉬운 성공으로 배율을 회복하더라도 이 상한은 넘지 않게 한다.
4. **목표가 과했던 경우:** 인증된 최선 배치를 기준으로, 실패한 축소보다 작은 축소 목표를 실제로 다시 만든다. 실패한 배치는 재사용 후보로 별도 보존한다.

목표 재설정 예시는 다음과 같다. 수치는 동작 설명용이며 새 기본값 제안이 아니다.

```text
인증된 길이 6,500mm → 6,480mm에 도전 → 분리 실패
인증된 6,500mm 배치를 복원 → 6,490mm에 다시 도전
성공하면 10mm 축소의 성과를 보존한 뒤 다음 축소량 판단
```

이때 6,480mm 실패는 ‘그 길이에 해가 존재하지 않는다’는 증명이 아니다. 이분 탐색처럼 불가능한 하한으로 영구 고정해서는 안 된다. 새로운 좋은 배치나 충분한 여유가 생기면 재도전할 수 있어야 한다. 현재 폭 진동·완화 복구와 새 제어기가 동시에 같은 실패에 반응해 목표를 중복 변경하지 않도록 한곳에서 결정해야 한다.

시간에 따른 상한의 개념은 아래와 같다. 구체적인 감쇠 곡선과 계수는 비교 시험 후 정해야 한다.

```text
다음 step = min(최근 인증 성공·실패 비용으로 제안한 step,
                Explore 진행도에 따라 낮아지는 step 상한)
```

이는 **step이 한 번도 커지지 않는 강제 단조 감소**와는 다르다. 충분히 쉬운 성공에는 작은 회복을 허용하되, 후반에 다시 과도하게 커지는 것을 상한으로 막는다. 단순 시간 감쇠도 별도 대조 실험으로 비교할 가치가 있다.

여기에도 중요한 한계가 있다. `separate()` 한 번이 남은 시간을 거의 다 쓰면, 밖에서 다음 step을 계산해도 늦다. 현재 목표의 장기 정체를 완화하려면 4절의 작업 예산·안전한 반환 경계와 연계해야 한다. **분리 중인 워커의 strip을 외부에서 바꾸는 방식은 사용하지 않는다.** 자연 반환 또는 안전하게 끝낸 경계에서만 재설정한다.

제어 계산 자체는 시도 경계에서 몇 개의 값만 갱신하므로 작게 만들 수 있다. 실제 성능 영향은 추가 배치 복원, 재시도 횟수, 너무 작은 축소로 늘어나는 인증 횟수가 좌우한다. 속도·수율 개선 여부는 아직 미측정이다. 기존 Config를 바꾸는 것으로 해결을 대신하거나 새로운 컴파일 기능을 요구하는 제안은 아니다.

## 9. 먼저 완료된 워커의 충돌 없는 결과를 콜백으로 보낼 수 있는가

### 9.1 가능하지만 ‘조각 하나의 성공’과 ‘전체 배치의 성공’을 구분해야 한다

**가능하다. 동기식 라운드의 승자 결정과 다음 탐색은 유지하면서, 먼저 확보한 인증 배치를 별도 경로로 먼저 알릴 수 있다.**

단, 다음은 전송 가능한 완성 결과가 아니다.

- 한 조각의 후보 검사만 충돌 없이 끝난 상태.
- 조각 일부만 옮긴 결과를 다른 워커의 결과와 합친 배치.
- 전체 tracker loss가 0이지만 원본 겹침·잠금·그룹·회전 인증은 하지 않은 상태.

워커는 전체 배치의 독립 복사본을 가진다. 먼저 끝난 워커의 **전체 배치 스냅샷**을 인증해서 보낼 수 있다. 조각 사이의 허용 겹침과 잠금 예외는 현재 계약대로 유지한다. 여기서 ‘충돌 없음’은 기하 교집합이 무조건 0이라는 뜻이 아니라, 현재 허용 규칙에 대한 정밀 검증 통과를 뜻한다.

### 9.2 현재는 왜 보내지 못하는가

`move_items_multi()`는 `par_iter_mut().map(...).collect()`가 모두 완료된 뒤에야 반환한다. 워커의 `move_items()` 안에는 외부 솔루션 콜백이 없다. 이후 승자를 선택하고, `separate()`의 원본 보정 및 Explore 인증을 거쳐 `ExplFeas`가 보고된다.

또한 현재 listener는 `&mut` 인터페이스이고 FFI 구현은 `Rc<Cell<...>>`, `Rc<RefCell<...>>`를 사용한다. **여러 Rayon 워커가 현재 listener를 직접 동시에 호출하도록 연결할 수 없다.** 포인터를 강제로 전달하거나 `unsafe Send`를 붙이는 해결은 부적절하다.

### 9.3 추천 구조: 계산은 동기식, 인증 결과 전달은 완료 시점에

```text
워커 A 완료 → 전체 loss=0 후보 → 불변 스냅샷 → 정밀 인증 → 조정자 → 콜백
워커 B 계산 ─────────────────────────────────────────── 계속
워커 C 계산 ─────────────────────────────────────────── 계속
모두 완료 → 기존 순서·기준으로 라운드 승자 선택 → 다음 라운드
```

구체적으로는 다음 책임을 나눈다.

1. 완료한 워커가 loss=0인 경우에만 불변 배치 후보를 만든다. 워커가 계속 수정할 tracker나 layout에 대한 참조는 전달하지 않는다.
2. 완료 워커의 여유 또는 제한된 검증 경로에서 전체 정밀 인증을 수행한다. 원본 한도 검사, 완전한 조각 수, 유한 좌표, 회전, 잠금 및 그룹 조건을 모두 포함한다.
3. run·phase·round 식별자와 함께 결과를 조정자에게 전달한다. 콜백은 단일 소유 스레드에서 직렬로 호출하고 기존 JSON 형식을 사용한다.
4. 다른 워커를 취소하거나, 완료한 워커가 다음 라운드로 먼저 가도록 하지 않는다. 기존 난수 진행과 라운드 승자 선택을 보존한다.
5. 새 인증 결과를 권위 있는 최선 체크포인트에 반영한 뒤 공개한다. Stop, 단계 종료, 최종 GetSolution 및 내보내기도 같은 최선 결과를 보존한다.

**채널만 추가하고 현재 `collect()` 뒤에서 읽으면 조기 전달이 되지 않는다.** 조정자가 계산 완료를 기다리는 동안에도 결과를 받을 수 있도록 실행·대기 경계를 재구성해야 한다. 예를 들어 listener를 원래 소유 스레드에 남겨 두고 워커 라운드 실행과 결과 수신을 분리하는 구조를 검토할 수 있다. listener를 그대로 다른 스레드로 옮길 수 있다는 뜻은 아니다.

모든 Rayon 스레드가 작업하는데 그 안에서 조정자가 blocking receive로 자리를 점유하면 1워커 환경 등에서 진행을 막을 수 있다. 조정자의 대기는 기하 워커 풀 밖에서 처리하고, 라운드마다 새 OS 스레드를 만드는 방식은 피해야 한다. 워커의 오류·panic·취소 시에도 완료 통지를 받아 대기가 끝나도록 설계해야 한다.

### 9.4 원본 보정과 공개 결과 보존

현재 원본 보정은 전체 워커 결과를 합친 뒤 실행되는 경로에 있다. 조기 후보가 원본 검사에 실패하면, **첫 버전에서는 조기 공개를 생략하고 기존 분리 후 보정 경로에 맡기는 것이 적절하다.** 보정을 각 워커에서 별도로 실행하면 계산량·좌표·선택 경로까지 달라져 작업 범위가 커진다.

또한 현재 인증 캐시는 새 후보를 인증하고 저장하지만, 임의 순서로 도착하는 여러 워커 결과의 ‘가장 짧은 길이’를 자동으로 보장하는 일반 우선순위 큐는 아니다. 새 비동기 전달 경로에는 명시적인 비교와 버전 관리가 필요하다.

- 같은 실행의 완전한 인증 결과 중 더 짧은 길이를 우선하고, 같은 길이는 불필요한 화면 교체를 줄인다.
- 오래된 실행의 콜백, 늦게 온 이전 후보, 폭 완화로 더 길어진 결과가 공개 최선을 덮어쓰지 않게 한다.
- 콜백만 새 결과를 보관하고 솔버의 최종 반환은 예전 결과를 선택하는 상태를 만들지 않는다.
- Stop 전에 이미 인증·채택한 결과는 보존한다. 인증이 끝나지 않은 후보를 Stop 때문에 검증 없이 올리지 않는다.
- 여러 후보를 하나로 줄일 때 미인증 후보가 다른 인증 가능 후보를 영구적으로 막지 않게 한다.

FFI의 기존 `ExplFeas` JSON 정책도 경로별로 다르다. structure-first는 인증 JSON을 보낼 수 있지만 일반 legacy 경로는 `emit_feasible_json`이 꺼진 구성이 있다. 이벤트만 추가하고 JSON을 싣지 않으면 WPF는 형상을 갱신하지 않는다. 현재 JSON 계약과 OrgID 등의 직렬화 경로를 유지하고 해당 보고 경로까지 연결해야 한다.

WPF에는 실행 세대와 비동기 파싱 순서를 확인하는 처리가 있지만, 이것이 native 콜백의 다중 스레드 호출이나 최종 결과 역행까지 자동으로 해결하지는 않는다.

### 9.5 얻을 수 있는 효과와 비용

효과는 **충돌 없는 배치를 발견한 시점과 화면에 표시하는 시점의 간격을 줄이는 것**이다. 기존 승자 선택을 그대로 유지한다면 이 기능 자체가 다음 shrink를 앞당기거나 탐색 처리량을 늘리는 것은 아니다.

어떤 라운드에서 A가 100ms에 끝나고 마지막 워커가 500ms에 끝났다고 하자. A의 전체 배치가 인증 가능하다면 최대 400ms의 대기 구간 일부를 앞당겨 활용할 수 있다. 실제 이득에서는 스냅샷·인증·JSON·UI 전달 시간을 빼야 한다. 이 수치는 예시이며 측정값이 아니다.

특히 모든 워커의 loss가 계속 양수인 어려운 분리 과정에서는 보낼 수 있는 새 무충돌 결과가 없다. 먼저 나온 loss=0 후보가 있으면 현재 방식도 해당 라운드 종료 후 성공 처리를 시작하므로, 주로 줄일 수 있는 것은 **그 성공 라운드의 마지막 워커를 기다리는 시간**이다. 긴 분리 전체의 대기 시간을 없애는 것으로 이해하면 안 된다.

비용을 제한하려면 전체 loss=0 후보에만 스냅샷과 인증을 수행하고, 같은 길이의 이미 인증된 결과는 중복 보고를 줄이며, 대기열 크기와 전송 빈도를 제한한다. 인증 캐시가 thread-local인 부분은 워커에서 인증했다고 조정자에서 자동 적중하지 않는다. 스냅샷에 정확히 연결된 인증 증거 전달 또는 동일 경로의 재검증 여부도 설계해야 한다. 여유 워커에서 검증하더라도 다른 워커와 메모리·CPU 자원을 공유하므로 비용이 무료는 아니다.

## 10. 추가 제안의 시험 순서

두 기능은 독립적으로 시험해야 한다. shrink 정책은 수율·탐색 경로를 바꾸고, 조기 콜백은 주로 결과 표시 지연을 바꾼다.

| 시험 | 확인할 지표 | 채택 판단 |
|---|---|---|
| 현재 DensityLegacy 기준선 | 인증 길이 이력, 목표별 실제 축소 mm, 분리 시간·평가 수·재시도 | 새 실험과 같은 초기 배치·seed·CPU 예산 사용 |
| 단순 시간 감쇠만 적용 | 목표 수율 도달 시간, 최종 길이, 너무 작은 축소 반복 수 | 사용자의 ‘초반 크게, 후반 작게’ 가설을 분리 평가 |
| 실패 시 실제 목표 backoff + 느린 회복 | 과한 목표에서 소비한 시간, 복원 비용, 인증 성공률 | scale 값만 줄고 목표가 그대로 남는 문제가 해소되는지 확인 |
| 난이도 피드백 + 시간 상한 | 앞 두 방식 대비 품질·도달 시간 | 복잡성을 추가할 실익이 있을 때만 채택 |
| 동기식 유지 + 조기 인증 콜백 | 최초 후보 완료→인증→콜백→화면 시각, 중복 인증 비용, 전체 길이 | 표시 지연 개선과 Stop·최종 결과 비퇴행 확인 |

shrink 실험은 같은 seed라도 탐색 경로가 바뀌는 것이 정상이다. 여러 입력과 시간 예산에서 최종 길이·목표 도달 시간을 비교해야 한다. 단순 후보 평가 처리량만으로 판단하지 않는다. 콜백 실험은 고정 반복에서 워커의 RNG·승자 선택을 보존하는지 확인하고, 시간 제한 실행에서는 인증 비용이 최종 수율을 떨어뜨리지 않는지도 확인한다.

추가 측정은 매 후보에 로그를 쓰는 방식 대신 시도·라운드 경계 중심으로 구성한다. 시간 감쇠는 실제 phase deadline을 기준으로 하며, 명확한 deadline이 없는 호출에서는 동작 방식을 별도로 정의해야 한다. 새 step이 f32에서 길이를 실제로 줄이지 못하는 경우와 잠금 하한도 처리해야 한다.

**추가 분석의 추천은 ‘인증 성공·실패 비용으로 축소량 조절 + 후반 step 상한 감소’와 ‘동기식 계산을 유지한 조기 인증 결과 전달’이다.** 전자는 과도한 축소 시도의 비용을 줄이는 목적이고, 후자는 이미 얻은 결과를 더 빨리 보여주는 목적이다. 아직 두 기능을 구현하거나 성능·Stop 경로를 시험한 상태는 아니다.
