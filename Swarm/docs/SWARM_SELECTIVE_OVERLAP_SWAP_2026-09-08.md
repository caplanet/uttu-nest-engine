# Swarm 선택적 겹침 보호·SWAP 비교 — 2026-09-08

> 상태 변경: 2026-09-08 사용자 요청으로 선택적 직선·정점 보호를 롤백했다. 현재 코드는 직전의 균일 `piece_overlap_mm` 원본 검사·보정 방식이다. 아래 내용은 당시 시험 기록이며 현재 동작 설명이 아니다. [롤백 기록](SWARM_UNIFORM_OVERLAP_ROLLBACK_2026-09-08.md)

기존 상태의 소스와 Rust/WPF 실행본을 백업한 후, **유지된 직선과 정점을 보호하고 단순화로 바뀐 구간만 겹침을 허용**하도록 구현했다. 허용 한도는 계속 기존 `piece_overlap_mm`를 사용한다. Config 필드·기본값·ABI는 변경하지 않았다. 자동 롤백이나 외부 Uttu.Nest 배포는 하지 않았다. 유지/롤백 결정은 사용자에게 남긴다.

## 보호 규칙

Swarm 입력에는 CAD의 직선/곡선 속성이 없다. 입력 원본 폴리곤을 단순화한 **축소 전 기준 형상**과 비교해 판별한다.

- 원본 변의 두 끝점이 같은 단순화 기준 변 위에 남으면 그 원본 변 전체를 보호한다. 중간의 일직선 정점만 제거된 경우에도 직선은 보호된다.
- 단순화 후에도 같은 위치에 남은 원본 정점을 보호한다. 원본 변이 바뀌었더라도 그 끝 정점은 별도로 보호한다.
- 나머지 구간은 `piece_overlap_mm` 범위의 겹침을 허용한다. 상대 조각의 보호 변/정점을 침범하면 거절한다. 두 조각의 원본 교집합을 허용치 절반만큼 안쪽으로 offset했을 때 영역이 남는지도 검사한다.
- 원본은 **Swarm이 수신한 원본 폴리곤**이다. Uttu.Nest에서 Swarm으로 보내기 전에 이미 삭제한 정점이나 CAD 곡선 속성을 복원하지 않는다.

따라서 5mm 입력은 “모든 변에서 5mm 허용”을 뜻하지 않는다. 유지된 직선/정점에서는 겹침을 막고, 변경 구간에서도 최대 한도만 5mm다. 단순화 오차와 보호 구간 배치에 따라 실제 허용 가능한 겹침은 더 작다. 1/3/5mm의 동적 입력은 시험으로 확인했다.

판별 오차는 0.0005mm, 정밀 교집합 격자는 0.0001mm다. 보호 구간은 원본 내부에 잘라낸 0.001mm 두께의 띠로 검사한다. 경계 접촉은 면적 0으로 허용하며, 격자 오차를 포함한 수치 검사이지 무한 정밀도 보장은 아니다. 이 수치들은 새로운 겹침 허용 Config가 아니다.

## 탐색·결과 경로

`original_overlap/protection.rs`에서 단순화된 형상의 내부 축소분에 보호 변/정점 주변의 원본 재료를 합쳐 `shape_cd`를 만든다. Explore·Compress·Polish의 CDE 및 이 형상을 읽는 NFP 준비부터 보호 구간이 반영된다. 탐색 형상의 연결성과 안정성을 위해 보호부는 원본 검사 띠보다 넓게 유지하므로, 정밀 검사상 허용 가능한 일부 자세도 탐색 단계에서는 보수적으로 거절할 수 있다. 합친 형상이 분리되거나 유효하지 않으면 축소하지 않은 기준 형상을 사용하고, 구멍은 채워서 보수적으로 처리한다.

원단 컨테이너는 명목 크기를 유지한다. 선택적으로 축소된 조각의 **원본**이 원단을 벗어나는 경우는 원본 인증에서 거절한다. Init 보정, Separator 분리, 단계 결과 인증, 콜백·내보내기의 기존 공통 인증 경로에 동일한 원본 보호 규칙이 적용된다. 보정 실패/취소 시 입력 배치로 되돌아가는 트랜잭션과 최종 인증을 유지한다.

잠금/잠금 겹침과 잠금 조각의 원단 이탈은 기존 허용 정책을 유지한다. 잠금/이동 조각 쌍은 검사하고, 보정 중 잠금 좌표와 강체 그룹의 상대 좌표는 유지한다.

## SIMD와 병렬화

- 조각별 보호 탐색 형상 준비 및 원본 보호 띠 준비를 Rayon으로 병렬 처리한다. mm 단순화 경로에서 같은 형상을 두 번 단순화하던 중복도 피했다.
- 검사 중 서로 독립적인 미캐시 충돌 쌍이 64개 이상이면 병렬 계산하고, 캐시 기록과 위반 목록 반영은 합류 후 수행한다. 작은 작업은 직렬로 처리한다. 작업 중 취소 신호도 확인한다.
- 기존 원본 정점 변환·경계상자 SIMD를 유지하고, 보호 띠의 f64 좌표 변환에 4개씩 처리하는 SIMD를 추가했다. f32로 다시 줄이거나 FMA 근사로 판정 경계를 바꾸지 않는다. `simd` 기능 없는 빌드에는 스칼라 경로가 있다.

동일한 공개 좌표 배치들을 대상으로 기준본/SIMD본/스칼라본을 순차·역순으로 실행했다. 프로세스당 조건별 20회 × 5라운드, 빌드별 2프로세스의 라운드 중앙값이다. 원본 검사와 전체 결과 검증을 분리했다. 측정 중 다른 빌드/벤치마크를 병행하지 않았다.

| WSjk 156조각, 호출당 | 변경 전 균일 허용·1스레드 | 선택 보호·1스레드 | 변경 전 균일 허용·4스레드 | 선택 보호·4스레드 |
|---|---:|---:|---:|---:|
| 최초 원본 검사: 보호 형상 준비 포함 | 4.947ms | 15.518ms | 5.008ms | 7.602ms |
| 배치가 바뀌는 원본 검사 | 3.221ms | 4.120ms | 3.411ms | 2.312ms |
| 같은 배치 캐시 검사 | 0.052ms | 0.061ms | 0.082ms | 0.112ms |

선택 보호 기능 안에서 1→4스레드는 변경 배치의 원본 검사를 **43.9%**, 최초 검사를 **51.0%** 줄였다. 변경 전 균일 허용과 비교하면 1스레드 변경 검사는 27.9% 비싸지만, 4스레드는 32.2% 저렴했다. 최초 보호 형상 준비 비용은 증가한다. TLS/Separator 캐시를 재사용하는 정상 반복에서 매번 최초 준비 비용을 내지는 않는다.

선택 보호본의 전체 결과 검증은 1스레드 7.807ms, 4스레드 5.671ms였다. **변경 전 전체 검증과의 배수 비교는 하지 않는다.** 같은 WSjk 좌표가 변경 전 탐색 형상에서는 CDE를 통과하지 못해 200/200회 조기 거절됐기 때문이다. 원본 검사만의 비교에서는 양쪽 모두 200/200회 통과했다. 64조각 바지의 전체 검증은 양쪽 모두 통과했으며, 4스레드에서 변경 전 1.741ms → 선택 보호 1.147ms였다.

SIMD만의 효과는 제한적이다. WSjk 4스레드 원본 검사는 스칼라 2.439ms → SIMD 2.312ms였지만 전체 검증은 5.489ms → 5.671ms로 편차가 섞였다. SIMD 단독의 확실한 전체 속도 향상이나 전체 네스팅 처리시간의 특정 감소율을 주장하지 않는다.

## SWAP 효율 비교

실제 제품 소스 복사본에만 측정용 차단/집계 코드를 넣었다. 제품 Config나 알고리즘 선택 기본값을 바꾸지 않았다. 시드 17/31/73, PolySimpl 0.01, overlap 5mm, Explore 8초·Compress 4초·Polish 2초, Rayon 4스레드·Separator worker 1로 순차 실행했다. 시드별 네 가지 모드의 **Init 좌표·폭이 완전히 동일함**을 확인했다.

- WSjk: 156조각, 원단 높이 1524mm, 입력 정점 33,477개, 보호 탐색 정점 3,448개.
- 바지: 저장소 `trousers.json`을 20배 확대해 원단 높이 1580mm로 만든 64조각 입력. 5mm가 입력 축척에 비해 과도해지는 것을 피한 시험 데이터다.
- 두 종류의 SWAP OFF / 탐색용만 ON / Separator만 ON / 둘 다 ON: 총 24회. R&R 설정은 그대로이며 이 시간 예산에서 실제 적용 횟수는 0이었다.

표의 변화는 OFF 대비 최종 원단 길이 변화다. **음수면 절약, 양수면 악화**다. 수율은 원본 조각 면적 합 ÷ (명목 원단 높이 × 사용 길이)다.

| 입력 | 모드 | 길이 변화 중앙값 | 수율 변화 중앙값 | 길이 개선/악화 |
|---|---|---:|---:|---:|
| WSjk 156 | Separator만 | +0.861% | -0.578%p | 0 / 3 |
| WSjk 156 | 둘 다 | -0.050% | +0.034%p | 2 / 1 |
| 바지 64 | 탐색용만 | -0.125% | +0.111%p | 3 / 0 |
| 바지 64 | Separator만 | +0.172% | -0.154%p | 1 / 2 |
| 바지 64 | 둘 다 | +0.368% | -0.327%p | 1 / 2 |

WSjk에서 탐색용 SWAP은 한 번도 실행되지 않았다. 해당 모드의 약 1% 차이는 실행 시간/스케줄링에 따른 시도 횟수 차이이며 SWAP의 개선 효과로 집계하지 않는다. 이 때문에 작은 시간제한 시험의 수치만으로 일반적인 우열을 주장하지 않는다.

탐색용 SWAP은 바지에서 실제 3회 적용됐다. 그중 1회는 **후속 분리 → 정밀 인증 → 더 짧은 폭의 채택**까지 확인했다. 나머지 2회는 시간 내 인증된 개선으로 집계되지 않았고 최종 결과는 인증된 incumbent를 유지했다. 성공 사례인 seed 17의 탐색용 모드는 OFF 대비 4880.293 → 4874.214mm, **6.080mm 감소**, 수율 89.2585 → 89.3698%였다. 이 최종 차이 전체를 단일 SWAP의 순수 효과로 분리한 측정은 아니며, 내부 채택 계측으로 SWAP 뒤 실제 폭 개선이 있었다는 점은 확인했다.

Separator SWAP의 내부 채택은 합계 39회다. 이는 충돌 비용 조건을 통과한 횟수이며 최종 수율 개선 횟수와 다르다. **SWAP이 항상 길이를 줄인다는 결론은 아니다.** 특히 Separator 단독은 이번 두 입력의 중앙값에서 악화됐다. 따라서 이번 작업에서 SWAP 빈도/기본값을 더 공격적으로 바꾸지는 않았다.

## 독립 정밀 검사와 빌드

모든 실행의 Init·Explore·Compress·Polish 96배치, 10,560개 배치를 GEOS/Shapely 2.1.2로 검사했다. 공개 좌표를 원본 폴리곤에 적용해 보호 선분/정점을 상대 폴리곤 내부와 직접 비교한다. Rust의 보호 띠를 재사용하지 않는다. 접촉/격자 오차용 0.0002mm, 원단 경계 0.0006mm의 검사 공차를 명시했다.

- 보호 변·정점 침범: 0.
- 입력 한도 5mm 초과: 0.
- 이동 조각의 원단 이탈: 0.
- 원본 겹침이 있는 쌍은 단계 합계 287개, 독립 최대 겹침 깊이 3.679980mm. 변경 구간에서 실제 겹침 허용이 작동한다.
- 수치 결과 검사이며 Uttu.Nest 화면을 직접 실행해 육안 확인한 결과는 아니다.

최종 검증은 core 732건 + Native 101건 + 관련 통합시험 22건, **총 855건 통과**다. 기존 ignored 시험 14건은 실행하지 않았다. 원본 예산 1/3/5mm, 유지 정점 단독 침범, 곡선 변경부의 실제 허용, mm/면적 단순화 모드, SIMD/스칼라 비트 일치, 1/4스레드 판정 일치, 캐시, 잠금, 그룹, 취소, Compress/Polish·콜백·내보내기 경로를 포함한다. `selective-final-verified-tests.log`와 `selective-final-integration.log`에 결과를 보관했다.

Rust는 `cargo build -p swarm --release --features "simd,capmods,adaptive,structure-first,jni" --offline`로 빌드했다. 현재 프로필의 `opt-level=3`, **`lto="fat"`**를 적용했다. `codegen-units=1`은 현재 Cargo.toml에서 주석 상태이며 이 작업에서 바꾸지 않았다. 링크 라이브러리 생성 안내 warning 1건, 오류 0건이다. WPF는 `dotnet build ...csproj -c Release -p:Platform=x64 --no-restore`로 빌드했고 이번 증분 빌드는 경고/오류 0건이다.

산출 DLL과 WPF에 복사된 DLL의 SHA-256 일치 및 작업 전 DLL과의 차이를 확인한다. ABI handshake는 15 / Config 776bytes / Structure 116bytes / features 0x1F(JNI 포함)다. 경로·해시는 `candidate-manifest.json`, 빌드 로그는 `target/selective-rust-release-build.log`와 `target/selective-wpf-release-build.log`다.

Windows에서는 `python -X utf8`로 실행한다. 준비 스크립트는 기존 증거 폴더 덮어쓰기를 거절한다.

재현 빌드는 **각 복사본에 서로 다른 `--target-dir`**을 지정해야 한다. 이번 비교 빌드의 실행 파일은 매번 해당 core를 컴파일한 뒤 별도 파일로 고정했고, 해시·선택 보호 프로파일·서로 다른 판정 결과를 보관했다. 이후 제품 Native 시험에서 공유 target 캐시의 변경 전 core가 재사용되어 명목 경계 시험이 실패한 문제가 발견됐다. 제품 패키지 캐시를 정리한 뒤 현재 소스를 재컴파일해 855건 시험과 DLL 빌드를 통과했다. 이 중간 실패 로그도 보존한다.

롤백은 이 스냅샷을 기준으로 이번 변경 파일만 복구하고, 작업 후 추가 변경이 있는지 먼저 대조해야 한다. 백업 WPF를 확인할 때는 ZIP을 별도 폴더에 풀어 그 폴더의 EXE를 실행할 수 있다. 이번 작업본과 변경 전 실행본을 모두 보관하며 유지/롤백을 자동 결정하지 않는다.
